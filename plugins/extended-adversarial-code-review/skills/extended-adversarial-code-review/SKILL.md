# Extended adversarial code review

**A review loop with no declared stopping rule does not
converge. It diverges, because fixes written under review
pressure carry defects at a higher rate than the original
code did.**

Everything here is measured from one episode: eight rounds
against one 2,500-line program in a single day. 224 review
agents, 15.0M subagent tokens, 3.6 hours of review and 2.8
hours of fixing. The operator stopped it, and was right to.

The episode's data is private and is not published with this
skill. Treat every figure below as one operator's report
from one loop, not as a benchmark.

Read this before dispatching the first round. Every
expensive mistake below was made before any agent ran.

## What the episode measured

| Round | Claims raised | Survived refutation | Distinct defects fixed | Fixed defects that an earlier fix had caused |
| ----- | ------------- | ------------------- | ---------------------- | -------------------------------------------- |
| 4     | 40            | 21                  | 17                     | 2                                            |
| 5     | 40            | 24                  | 23                     | 1                                            |
| 6     | 45            | 26                  | 14                     | **3 of 8 highs (37%)**                       |
| 7     | 37            | 23                  | 14                     | 5                                            |
| 8     | 20            | 3                   | 3                      | 1                                            |

Survivors stayed between 21 and 26 through round 7. Across
rounds 4 to 8, **17% of fixed defects and 28% of fixed
high-severity defects were created by an earlier fix in the
same loop.** Cost of a high-severity defect that the loop
did not itself cause: **590,000 subagent tokens.**

**84% of all fixes were "add another case."** Two were
changes of approach, and those two delivered more than the
other eighty combined: one eliminated a defect class
permanently, the other cut a false-positive rate from 86% to
zero.

## Before you dispatch anything

### Name the adversary, out loud, in one sentence

Write down who the attacker is and what they control. Then
check the sentence is true.

The most expensive error available here is running an
adversarial review against a non-adversarial input. If the
input is generated by you, assembled from context you chose,
or produced by a trusted upstream, nobody is crafting
anything to defeat your checks. The review is about
**accident**, and the search space for accident is finite.

The search space for **evasion** is not. An agent asked "how
could someone get X past this?" will always answer,
plausibly, forever. Every answer looks like a defect. None
of them terminate.

| If the adversary is         | The review asks           | Search space                                           |
| --------------------------- | ------------------------- | ------------------------------------------------------ |
| A stranger submitting input | What gets through?        | Unbounded — bound it by refusing what you cannot parse |
| A careless colleague        | What breaks by accident?  | Small — enumerate it                                   |
| You, last week              | What did I get wrong?     | Small — the diff                                       |
| Nobody                      | Nothing. Do not run this. | —                                                      |

In the measured episode the adversary was nobody: the
documents under review were generated from context the
author assembled. The nine decoding surfaces built to defeat
evasion became the program's largest source of new defects.

### Declare two numbers before round one

Both are unrecoverable afterwards, and their absence is
itself the defect.

- **A token ceiling per net-new high-severity defect.** When
  the loop crosses it, stop. The episode reached 590k per
  defect with no ceiling declared.
- **Whether the fix domain is enumerable.** If the highest
  severity finding's fix is "handle one more member of a set
  with no enumeration" — encodings, escapings, markup
  constructions, protocol shapes — the loop cannot
  terminate. This check would have fired at **round 4**, the
  earliest of any signal.

### Say the price before the round, not after

Roughly 2.7M subagent tokens and 35 minutes per round, plus
18 to 51 minutes of fixing. Re-quote it before each
subsequent round; a cost accepted once is not accepted four
times.

### Know that this loop is tighter than human review

In human review, one person writes, another reviews, a third
may fix. That separation does real work.

When an agent reviews an agent's code and applies its own
fixes, all three roles collapse into one set of priors. The
fix is written under time pressure by the party that
misunderstood the problem, and it goes unreviewed until the
next round — where it is the newest and least-examined code
in the program, which is exactly where the next defects are.

Measured: the original 814-line implementation yielded 7
confirmed defects to the first two rounds. The fixes,
totalling far fewer lines, produced 12 more. **Fixes were
more defective than the code they repaired**, which is why
this diverges rather than merely failing to converge.

Two cheap mitigations:

- **Never let a fix ship unpinned.** Every fix gets a test
  that fails without it, written before the next round.
- **Point one lens at the previous round's diff.** It is the
  highest-yield lens there is — see below.

## Structure a round so it can terminate

### Lenses, ranked by measured yield

| Lens                                     | Survival | Verdict                                                        |
| ---------------------------------------- | -------- | -------------------------------------------------------------- |
| **Review the previous fix's diff**       | 78%      | **Run this one.** Found 9 of the 15 self-inflicted defects     |
| "What can hide from this check?"         | 88%      | **Highest survival, worst net yield.** See below               |
| "What does this test fail to prove?"     | 67%      | Worth running                                                  |
| "What operational failure is unhandled?" | 62%      | Worth running                                                  |
| "Where do the docs and code disagree?"   | 42%      | **Do not.** Largest budget, lowest value, survivors were typos |
| Concurrency, generic operational sweeps  | 0%       | Returned nothing across 8 adjudicated claims                   |

**High survival is not evidence a lens is worth running.**
The 88% lens produced findings that were all real and all
one shape — "a term can hide in encoding X" — and each fix
added a surface. Nine surfaces later, that lens was the
direct cause of three high-severity regressions. Survival
measures whether a finding is true. It says nothing about
whether acting on it improves the program.

The one bounded lens wins because its subject is bounded: a
diff has edges, a program does not.

### Every lens gets a paired inverse

Adversarial review asks _what gets through?_ and never _what
gets wrongly refused?_ All the pressure runs one direction
and the code drifts toward over-strictness, each step
looking like a correctness win.

| Adversarial lens              | Its inverse                                                |
| ----------------------------- | ---------------------------------------------------------- |
| What input evades this check? | What valid input does this check refuse?                   |
| Where can this crash?         | Where does it report failure for something that succeeded? |
| What is not validated?        | What is validated more strictly than the thing it defends? |
| What does the gate miss?      | What does the gate hold that a person would pass?          |

Measured: over-strictness was **0% of fixes before the loop
began, and 29%, 21% and 33% of rounds 6, 7 and 8's fixes.**
The final test suite contains **19 tests whose only job is
to assert that something is _not_ refused**, including a
whole test class for one check. Every one was added after
the loop started. One predicate oscillated across five
consecutive commits because each round pushed it only one
way.

Weight inverse findings higher. Nothing else is looking for
them.

### Filter on severity, not on reproduction

| Claimed severity | Survival |
| ---------------- | -------- |
| critical         | 100%     |
| high             | 83%      |
| medium           | 57%      |
| low              | 47%      |

**Drop the low bucket unadjudicated.** The episode spent
roughly 53k tokens each on 47 low-severity claims that
survived at coin-flip rates.

Requiring reproduction by execution helps, but less than it
is usually claimed to: **69% survival for execution-backed
findings against 51% for reasoned ones — 18 points, not an
order of magnitude.** Require it anyway, because a
reproduction is what makes a finding cheap to act on. Just
do not treat it as the filter; severity is the stronger
signal and it is free.

### Deduplicate before adjudicating

**About a third of "survivors" in the later rounds were the
same defect found by a different lens.** One defect appeared
as three separate survivors in one round. No round had a
dedup step.

Dedupe by the fix, not by the description: two findings are
one if their fixes touch the same function. Do this in plain
code between the finder and the adjudication phase — it is a
set operation, not a judgment call.

And do not silently cap. The episode capped adjudication at
8 findings per lens and **discarded 74 raised claims without
reading them**, while paying full price to adjudicate
duplicates. If you cap, say what was dropped.

### Do not run a refutation phase

This contradicts the usual advice, including my own before I
measured it.

Refutation consumed **9.7M of 15.0M tokens — 65% of the
entire review budget — across 182 agents.** It removed 64 of
168 claims. Of the removals that can be checked against
later history, **67% were fixed anyway**, three of them in
the very next commit. Two refuters given the identical claim
in the same round returned opposite verdicts.

A refuter shares the finder's priors, its reading of the
code, and its blind spots. It is not an independent judge;
it is a second opinion from the same mind, sold at the price
of the first.

Read the findings yourself. Severity plus dedup plus your
own judgment removes the same claims more accurately, at
roughly a third of the cost.

If you keep a verification step anyway, make it worth
something: give the verifier a **different lens** from the
finder, and require it to produce a reproduction of its own
rather than an opinion.

### Independence is structural, not tonal

A reviewer reading an evidence set you assembled, under a
prompt you wrote saying what each artifact proves, inherits
your ontology and reads for confirmation. "Be skeptical"
reproduces the same traversal in a suspicious voice. This is
**frame capture**. It governs whether a round is worth
anything; it does not make a loop terminate.

Five inversions break it, as prompt rules:

1. **Evidence first, never claim first.** Inventory every
   artifact and write what each establishes _on its own_
   before reading any claim. A claim with no line is a
   finding; a line cited twice is a finding.
2. **One source, one claim.** Two artifacts means two
   claims.
3. **Every validation names its boundary** — the exact
   command, plus what it does not cover.
4. **Nothing upstream counts as support.** A prior verdict
   from the same provider may not be cited.
5. **Falsification quota** — N recorded refutation attempts
   including the failed ones.

Plus anti-anchoring: read the previous reviewer's draft
**last** and diff against it.

## Channels that beat another review round

Spend a fraction of round N+1's cost on these first. Each
found defects that multiple rounds of agent review did not.

### Run the code over a real corpus — do this first

Point it at every real input on disk. Count what it accepts,
what it refuses, and read the refusals.

Measured, and this is the largest single result in the
episode: over 4,533 real files the redirect check produced
**58 refusals of which 8 were genuine — an 86% false
positive rate.** Eight rounds of agents produced one claim
about it and never measured its size. The corpus also found
a false positive four earlier rounds had missed, and it is
the only evidence that licensed the program's single best
design change.

Cost: **92 seconds for 4,646 files.** Against 590k tokens
per defect from agent review.

It is also the only channel that finds over-strictness at
all, and it produces a _rate_ rather than an anecdote.

### Review the diff, not the program

Covered above as a lens because that is how it is dispatched
— but it belongs on this list too. 78% survival, 9 of 15
regressions, and it is bounded.

### Mutate the code and re-run the tests

Delete a line, invert a condition, gut a handler. Anything
that stays green is a test proving nothing.

Honest scope note: in this episode executed mutation found
one dead test that a reading lens had already found twenty
minutes earlier. The technique is cheap and worth running,
but **this episode does not establish that it finds things
reading cannot** — the lens instructed to execute mutants
was killed before it reported. Run it; do not oversell it.

### Ask the person a plain question

Human attention on the artifact is a review channel agents
do not replicate. In this episode a one-line question from
the operator surfaced a real third party's name sitting in a
test fixture in a repository that was about to be published.

**Five rounds, about 180 agents, 12.4M tokens, every one of
them reading that exact file. Zero claims about it.** Agents
review what the prompt frames. They do not notice what does
not belong.

The specific gap worth naming: **nobody reviews the test
data.** Fixtures are read as scaffolding, not as content
that ships.

### Read it as the recipient

Open the output the way the person receiving it will: the
rendered page, the sent message, the file name, the URL.
Reviewers read source; defects live in what gets delivered.

## Reading a round's output

### Shape before count

Before triaging anything individually, ask what shape the
findings share. If they all reduce to one sentence, you have
**one design defect presented N times**, and fixing them
individually guarantees the next round presents it again in
a form you did not enumerate.

The tell: your fix list reads as _add another case_. In the
episode, more than 60% of survivors shared one root cause
from round 5 onward.

A clean specimen. A hand-rolled HTML scanner was patched
three times running, each patch repairing the last:

1. Refuse any document with an unterminated `<`. Fixed a
   quadratic scan; refused ordinary files containing
   `if (i < 1)`.
2. Bound each tag slice to 8 KiB. Fixed that; hid every
   attribute past 8 KiB — exactly the input the check
   existed to examine.
3. Anchor the patterns at `^<img`. Fixed that; made two
   merged tags invisible, so the scan skipped them entirely.
4. Replace it with a real parser. **Closed five findings at
   once and the class they belonged to permanently.** No
   later round found another defect of that kind.

Three rounds went into steps 1 to 3. Step 4 was available
throughout, and the signal was present from step 2: each fix
was a narrower special case than the one before it.

Step 4 was not free — it introduced three high-severity
regressions of its own. But those were _bounded_: the
parser's own semantics are a finite list. The class it
replaced was not.

**Prefer refusing input you cannot process over decoding
every possible encoding of it.** Refusal is finite and
checkable. Enumeration is not.

### Do not let the reviewer set the agenda

A round returns a list; the list is not a work plan. Triage
against product risk and be willing to fix two items out of
twenty.

Working the list in emitted order is how a program
accumulates a defence for every attack anyone imagined and
no coherent design.

### Track "survived" and "worth fixing" separately

They are different predicates and the episode's numbers
diverge in both directions. One high-severity claim survived
refutation in three consecutive rounds and was never fixed.
Two claims were declared unfixable limits and then fixed
eleven minutes later.

Never report a survivor count as a defect count.

### Name the boundary instead of chasing it

Some findings are real limits. Write each into the contract
in the reader's language and pin it with a test that fails
if it quietly becomes false.

Measured: the two limits documented this way were never
raised again across four subsequent rounds. Everything left
aspirational was re-raised.

### Do not let a fix commit assert a corpus result it did not re-run

One commit in the episode stated that every refusal was
genuine across some 4,500 files while its own corpus output
showed 58 refusals, 50 of them false. That claim sat in a
commit message a later reviewer would trust.

## The stopping rule

Stop when **any** clause fires. Ordered by when they fired
in the measured episode — the first two are the ones worth
having, because they fire before the loop has cost much.

1. **Unbounded domain.** The fix for the round's
   highest-severity finding is "handle one more member of a
   set that has no enumeration." — _fires at round 4_
2. **One shape.** 60% or more of the round's survivors share
   a root cause, judged by whether their fixes touch the
   same function or extend the same list. — _fires at round
   5_
3. **Self-feeding.** The round fixed a high-severity defect
   that an earlier fix in this loop introduced. — _fires at
   round 6, the only round whose high-severity repairs were
   counted separately_
4. **Net negative.** More than a quarter of the round's
   fixes were undoing earlier rounds. — _fires at round 7_
5. **Flat yield.** Distinct defects fixed has not risen for
   two rounds. Count fixes, never claims; claim counts stay
   high indefinitely. — _fires at round 7_
6. **Nothing user-visible.** Two consecutive rounds produced
   no finding that changes what a person experiences.
7. **Budget.** Cumulative tokens per net-new high-severity
   defect exceeds the ceiling you declared at the start.
8. **Nothing fixed.** The round applied no fixes; another
   round would re-read unchanged code. Hand the findings back.

The episode's own retrospective rule caught only clause 3
and would have saved one round. **Clauses 1 and 2 would have
saved three rounds, roughly 8M tokens and 3 hours.**

`scripts/round_yield.py` evaluates all eight from a small
per-round JSON record. Keep the record; none of it is
reconstructable afterwards. Record each round in
`rounds.json` and run `round_yield.py` on it after every
round; if it says STOP, stop.

**Report non-convergence the first time you see it, not the
fourth.** Two non-improving rounds are enough. The operator
cannot see the yield curve — you can, and billing further
rounds while staying quiet about it is the failure this
skill exists to prevent.

## Failure modes

| Failure                               | What it looks like                                                          | The fix                                            |
| ------------------------------------- | --------------------------------------------------------------------------- | -------------------------------------------------- |
| Adversarial frame on a friendly input | Endless plausible evasion findings                                          | Name the adversary first                           |
| Reviewing your own fixes              | Round N finds a defect in round N-1's fix                                   | Clause 3                                           |
| One-directional pressure              | Code grows stricter; nobody notices until real inputs are refused           | Paired inverse lenses; corpus run                  |
| Enumeration instead of design         | Every fix adds a case; the surface count keeps rising                       | Clauses 1 and 2                                    |
| Trusting survival rate                | The highest-survival lens is the one wrecking the design                    | Judge lenses by net yield, not truth rate          |
| Paying for duplicates                 | Three survivors, one defect                                                 | Dedupe by fix site before adjudicating             |
| Silent capping                        | 74 claims discarded unread while duplicates are adjudicated                 | Say what was dropped                               |
| Refutation theatre                    | Two thirds of budget spent removing claims you would have declined anyway   | Adjudicate the findings yourself                   |
| Boundary rediscovery                  | A known limit returns each round as a new finding                           | Write it in the contract; pin it with a test       |
| Bounds added for cost                 | A limit that fixes a performance problem excludes the input the check needs | Run the fix on the real shape, not a minimal repro |
| Unreviewed test data                  | A real person's name lives in a fixture in a repo about to be published     | Review fixtures as shipped content                 |
| Silent non-convergence                | Four flat rounds, none reported as flat                                     | Quote the yield curve every round                  |

## Spend the budget in this order

From the measured yields, for a bounded budget:

1. **Corpus run.** 92 seconds. Found the two largest
   false-positive classes and the evidence for the best
   design change.
2. **Diff-scoped review of the last change.** 78% survival,
   9 of 15 regressions, bounded subject.
3. **Executed mutation sweep.** One test-suite runtime per
   mutant.
4. **Everything else** — and expect it to be
   noise-dominated. The four weakest lenses in the episode
   consumed roughly 5M tokens for net-negative value.
