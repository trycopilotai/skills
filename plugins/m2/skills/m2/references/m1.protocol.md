# m1 protocol

Goal: run one disciplined M1 manager-of-ICs lane. An M1 lane
shapes packets inside a single domain, owns a disjoint file
or validation scope, fans lower-level execution out to SWE,
test, and evidence workers, and exits every planning pass
with a dispatch-ready packet, an integration decision, or a
concrete blocker. In this protocol, `m1` means manager of
ICs. It is the per-lane role that `m2()` (manager of
managers) coordinates, so one `m1` lane is one lane inside
an `m2` run (`m1 ⊂ m2`).

`m1()` is the single source of truth for manager-of-ICs
behavior. `m2()` references this protocol instead of
restating it, so a spawned manager lane can be handed this
one file rather than the whole manager-of-managers conductor
protocol. That keeps each spawned subagent's prompt scoped
to exactly its lane.

Invocation contract
(`m1(charter_or_scope[, lane_role:ROLE][, plan_path:PATH][, write_scope:GLOBS][, gates:IDS])`):

- Required: one `charter_or_scope` argument. It is either a
  manager charter file path, for example a project
  `managers/*.gpt.md` charter, or an inline domain or scope
  description.
- Optional keyword arguments, each in `key:value` form:
  - `lane_role:ROLE`: one of the canonical lane roles from
    the BFS/DFS Portfolio Balance Contract in
    `references/m2.protocol.md`, with the same
    values mirrored in
    `references/m2-artifact-schemas.md`:
    `depth_lane`, `breadth_lane`, `stabilization_lane`, or
    `evidence_lane`. Default `depth_lane`.
  - `plan_path:PATH`: the plan or PROJECT file the lane
    draws scope and acceptance rows from.
  - `write_scope:GLOBS`: the disjoint write scope or file
    leases the lane owns.
  - `gates:IDS`: the gate ids the lane's next ready packets
    may change or evidence.
- Accept:
  - `m1(.agents/projects/example-project/managers/verification-manager.gpt.md)`
  - `m1(relay transport, lane_role:depth_lane)`
  - `m1(activity ui polish, lane_role:breadth_lane, gates:ui-stream)`
  - `m1(stabilize auth gate, lane_role:stabilization_lane, write_scope:src/net/http/**)`
- Reject an empty `charter_or_scope`, an unknown keyword
  argument, or a `lane_role` value outside the accepted
  `m1()` product-lane roles.

Lane role semantics:

- A `depth_lane` owns hard correctness, polish, regression
  repair, and current-blocker closure for the highest-risk
  active gate family.
- A `breadth_lane` owns a different customer or user
  journey, or a different gate family, so the product
  surface widens while deep work continues. Breadth lanes
  must still land real code, tests, browser evidence,
  integration, or blocker removal; they are not permission
  for status-only or docs-only activity to count as
  progress.
- A `stabilization_lane` keeps recently green or yellow
  blocking gates from regressing while new breadth opens.
- An `evidence_lane` proves an active depth, stabilization,
  or breadth lane with targeted tests, localhost or browser
  proof, screenshots, traces, or review bundles tied to the
  same gate ids.

Derived values:

- `M1_CHARTER`: resolved charter file path or inline scope
  text.
- `M1_LANE_ROLE`: resolved lane role; `depth_lane` when
  omitted.
- `M1_WRITE_SCOPE`: the lane's disjoint write or validation
  scope.
- `M1_GATES`: the gate ids the lane may change or evidence.
- `M1_PLAN_PATH`: the plan or PROJECT source for scope and
  acceptance.

Execution phases:

1. Phase 0 `Guardrails and scope`.
   - Read `AGENTS.md` and honor repo instructions.
   - Confirm the active worktree and that the lane has a
     safe, disjoint write or validation scope before any
     worker edit.
   - Resolve `M1_CHARTER`, `M1_LANE_ROLE`, `M1_WRITE_SCOPE`,
     and `M1_GATES` from the invocation.

2. Phase 1 `Charter resolution`.
   - Load the charter file, or synthesize a charter from
     `charter_or_scope` with a Mission, Responsibilities,
     Required Inputs, and Done Means.
   - Bind `M1_LANE_ROLE` to the lane role semantics above,
     which mirror the BFS/DFS Portfolio Balance Contract in
     `references/m2.protocol.md`.
   - M1 managers own packet shaping inside their domain:
     local design choices, file ownership, tests, acceptance
     evidence, browser-proof expectations, and lower-level
     SWE dispatch.

3. Phase 2 `Packet planning`.
   - For the lane's movable packets, unresolved blockers,
     and cross-team contract decisions, satisfy each of:
     - require the manager to produce enough implementation
       plan detail for its next safe reports or packets
       before those worker edits begin;
     - require the manager to identify exact file ownership,
       tests, blockers, and cross-team dependencies.
     - require the manager to name the gate ids its next
       ready packets are allowed to change or evidence.
     - require accepted interface contract records for new
       or changed structs, functions, routes, proto fields,
       JSON fields, and browser bridge symbols before worker
       dispatch.
   - Managers should shape only enough design to unlock safe
     SWE execution. Do not treat a fully polished manager
     packet as a prerequisite to every lower-level edit.
   - Managers must not let planning sprawl block obvious
     safe implementation. A packet may move once its local
     plan, file ownership, contracts, and required review
     are sufficient; it does not need a fully finished
     global planning pass for unrelated packets.
   - Managers may inspect code and run read-only checks.

4. Phase 3 `Fan-out execution`.
   - Once an M1 manager has a safe disjoint write scope or
     validation scope, it must prefer fanning out
     lower-level execution to one or more SWEs instead of
     holding detailed implementation reasoning centrally.
   - Treat parallelism as the default even inside one broad
     domain when it contains disjoint code, validation, and
     collaboration-artifact scopes. A manager may keep one
     SWE lane on code generation while another lane captures
     browser proof, prepares review artifacts, or validates
     prior diffs.
   - Managers should split code generation from companion
     collaboration work whenever scopes are disjoint.
     Companion collaboration work includes browser evidence,
     validation runs, screenshots, diff summaries, contract
     records, review prep, and handoff artifacts that
     materially help integration or recovery.
   - Collaboration artifacts are valuable when they sharpen
     review, integration, or resume quality, but they must
     run beside code generation rather than replacing it
     while safe code work remains.
   - Prefer each active manager to maintain a small rolling
     queue of ready packets rather than a single packet. For
     product work, that queue should usually include at
     least one code-generation packet and, when useful, one
     validation or collaboration-artifact packet.
   - When a packet can be exercised in browser or localhost
     form, managers should pair code work with a parallel
     verification or evidence packet whenever file scopes
     allow.
   - For browser-visible product streams, fresh screenshot
     proof is a first-class collaboration artifact. When a
     coherent visible slice is ready, at least one lane
     should capture current screenshots or equivalent visual
     proof from the same branch and localhost demo that
     produced the code.
   - For user-facing UI plans, require the UI manager to
     name a Visual Designer, UI/UX Designer, and UX Tester
     triad with iteration count, HCI criteria, screenshots,
     pass/fail/blocked rules, and artifact paths.
   - Do not launch `fanOut()` or `dispatch()` until the
     packet is dispatch-ready under the lane charter and,
     when running under `m2()`, the conductor or TL review
     gate has explicitly released that packet for worker
     execution.
   - If an `m2()` manager plan is still awaiting Phase 4
     TL/Uber TL review, exit with the dispatch-ready packet
     instead of starting worker adapters.
   - Fan lower-level execution out through `fanOut()` or
     `dispatch()`, and keep the SWE, test, and evidence
     workers concurrent whenever safe parallel work exists.

5. Phase 4 `Supervision`.
   - Require each active manager to maintain an explicit
     supervision row for every SWE, tester, evidence worker,
     reviewer, or delivery worker it owns: deliverable,
     current status, last check, next check, and the exact
     redirect to issue if the worker is idle.
   - Integrate, reassign, or close finished workers, and
     never leave the lane idle while safe work exists.

6. Phase 5 `Exit`.
   - Require each active manager to exit planning with one
     of:
     - a dispatch-ready SWE packet;
     - an integration decision on returned worker output; or
     - a concrete blocker with owner and next action.
   - When running under a project or `m2()` run, append the
     lane's deliverable, status, and next action to the
     durable event log or board view rather than relying on
     chat history.

Failure handling:

- If `M1_CHARTER` is missing or unreadable, stop and report
  it.
- If `M1_LANE_ROLE` is outside the canonical enum, stop and
  report it.
- If the lane has no safe disjoint write or validation
  scope, surface that as a blocker instead of editing shared
  files.
- If the lane spends two consecutive active passes without
  dispatching a SWE, integrating worker output, or recording
  a concrete blocker, rescope the lane or surface the
  blocker.

Relationship to `m2()`:

- `m2()` (manager of managers) owns run safety, priority,
  cross-manager arbitration, lease and integration ordering,
  lane balance across up to `RUN_NUM_M1S` lanes, and TL and
  Uber TL review through `l8()`. `m1()` owns one lane only.
- The conductor dispatches one `m1()` lane per movable
  domain and keeps the higher-level thinking in `m2()`.
- Related protocols: `fanOut()`, `dispatch()`, `l8()`, and
  `writeAC()`.

Examples:

- `m1(relay transport, lane_role:depth_lane)` runs
  one depth lane that hardens the relay transport and fans
  SWE work out beneath it.
- `m1(activity ui polish, lane_role:breadth_lane, gates:ui-stream)`
  opens a breadth lane on a different user journey while a
  depth lane keeps running.
- `m1(.agents/projects/example-project/managers/verification-manager.gpt.md, lane_role:evidence_lane)`
  runs the verification charter as an evidence lane.
