# m2 protocol

Goal: run a manager-of-managers execution system from one M2
plan entrypoint. In this protocol, `m2` means manager of
managers. It never means a milestone, the Mac host, or an
Apple-silicon chip (M1/M2/M3/M4/M5). `numM1s` counts
parallel M1 manager agents, not machines, CPU cores, or
simultaneous builds.

The protocol coordinates a top-level MoM coordinator,
subteam managers, TL reviewers, Uber TL `l8()` reviewers,
implementation workers, testers, verification workers, and
delivery workers. It is a control-plane protocol over the
repo's existing agent, worktree, dispatch, review, and
validation practices.

Invocation contract
(`m2(plan_path[, resume:RUN_ID][, iterations:N][, duration:D][, numM1s:M])`):

- Required: one plan path argument.
- Optional: one resume argument in the form `resume:RUN_ID`,
  `run:RUN_ID`, or `tick:RUN_ID`.
- Optional: one iteration goal in the form `iterations:N`,
  where `N` is a positive base-10 integer. `iterations:N` is
  the required target number of completed durable conductor
  ticks for this invocation. It is implemented by an
  invocation-local counter initialized to `0` after initial
  run setup. Every time a durable conductor tick completes,
  satisfies `Real Work Tick Contract`, and appends its
  canonical event, increment the counter by `1`, then
  immediately run the next tick while the counter is less
  than `N`. Support-only or admin-only ticks do not consume
  the iteration goal unless the human explicitly asked for
  that maintenance. `iterations:N` is not a soft cap and not
  permission to complete one bounded slice and stop while
  other safe packets can still move.
- Optional: one wall-clock goal in the form `duration:D`,
  where `D` is either `Nm` for minutes or `Nh` for hours and
  `N` is a positive base-10 integer. Normalize `duration:D`
  to `RUN_WALL_CLOCK_GOAL_MINUTES`. For example,
  `duration:240m` and `duration:4h` both mean a minimum
  wall-clock goal of 240 minutes for the current invocation.
  The wall-clock goal begins after invocation parsing and
  resume/run setup begin; it is satisfied only when elapsed
  wall-clock time is greater than or equal to the normalized
  minute goal.
- When both `iterations:N` and `duration:D` are supplied,
  they define a combined budget. The effective budget uses
  the larger implied effort under
  `Budget Endstate Planning Contract`, and the invocation
  continues under `Budget Exit Contract` until acceptance is
  met, terminal state, explicit human pause/stop, a true
  blocker, or the 110% overrun exit is reached.
- Any invocation with `iterations:N`, `duration:D`, or both
  is a budgeted invocation. Before product ticks begin, the
  conductor must convert the supplied budget into a concrete
  budget-to-endstate plan under
  `Budget Endstate Planning Contract`. In budgeted
  invocations, the top-line exit target is the budget plan's
  acceptance criteria plus the lease itself, not mere
  elapsed time, PR creation, queued CI, screenshot capture,
  or a clean non-stopping delivery event.
- Optional: one parallel M1 lane goal in the form
  `numM1s:M`, where `M` is a positive base-10 integer. When
  omitted, default to `numM1s:1`. `numM1s:M` specifies the
  requested number of parallel M1 manager-of-IC lanes for
  the current invocation. Each active M1 must own a unique
  lane with a distinct lane role, gate family, customer/user
  journey, or evidence scope. If fewer than `M` safe unique
  lanes can move, the conductor must run the safe subset and
  record the concrete write-scope, dependency, validation,
  capability, or capacity blocker preventing the rest.
- `numM1s:M` does not by itself multiply `iterations:N` or
  replace single-lane budget math. When the human or a plan
  capsule explicitly defines ticks as aggregate M1 work
  across lanes, such as
  `16000 ticks = 4 M1 lanes * 4 wall-clock hours * 1000 ticks/hour`,
  the conductor must treat the requested tick budget as
  aggregate M1 lane work for that invocation. It must record
  `aggregate_m1_ticks=16000` and `per_lane_ticks=4000`
  separately from the wall-clock duration. `duration:D`
  remains the wall-clock exit basis; for `duration:4h`, the
  110% overrun exit is 264 minutes. This aggregate
  interpretation is opt-in only when requested by the human
  or plan capsule.
- `m2(plan_path)` is an execution request by default. It
  first checks the plan's latest runnable resume-prompt
  pointer. If that pointer identifies a compatible
  non-terminal run or plan-level resume capsule, the saved
  prompt text becomes the effective execution prompt exactly
  as if the human pasted it with the bare invocation. If no
  compatible saved prompt exists, validate the plan, start a
  durable conductor run, and drive the plan toward terminal
  state for as many meaningful ticks as the current context,
  tools, and capability gates safely allow.
- Accept `m2(path)`, `m2("path")`, or `m2('path')`.
- Resolve and retain the plan path through the agent's host
  execution surface before starting or entering a
  devcontainer. Never derive the canonical plan root from a
  container user's `$HOME`.
- If the invocation begins while target-repository commands
  are already running through a devcontainer, keep the
  agent's host shell as the control surface for
  `~/<plan-store>` reads and writes. Route only
  target-repository commands through the repository's
  documented devcontainer command surface.
- Treat the normalized host plan path as host-only state. Do
  not pass it to a devcontainer command or require it to
  exist below the container user's home directory.
- Accept `m2(path, resume:RUN_ID)` to resume a durable run.
- Accept `m2(path, iterations:N)` to start a durable run and
  complete `N` increment-eligible real-work conductor ticks.
  When a compatible latest runnable resume prompt exists,
  resume that run or capsule and override only the saved
  tick goal with the supplied `N` for the current invocation
  unless a terminal state, explicit human stop, or real
  blocker ends the invocation first.
- Accept `m2(path, resume:RUN_ID, iterations:N)` and
  `m2(path, iterations:N, resume:RUN_ID)` to resume a
  durable run and complete `N` increment-eligible real-work
  conductor ticks unless a terminal state, explicit human
  stop, or real blocker ends the invocation first.
- Accept `m2(path, duration:D)`,
  `m2(path, resume:RUN_ID, duration:D)`, and any ordering of
  `resume:RUN_ID`, `iterations:N`, and `duration:D` with one
  plan path. Explicit `duration:D` overrides only the saved
  wall-clock goal for the current invocation unless a later
  resume-prompt regeneration intentionally records it.
- Accept `m2(path, numM1s:M)`,
  `m2(path, resume:RUN_ID, numM1s:M)`, and any ordering of
  `resume:RUN_ID`, `iterations:N`, `duration:D`, and
  `numM1s:M` with one plan path. Explicit `numM1s:M`
  overrides only the saved parallel M1 lane goal for the
  current invocation unless a later resume-prompt
  regeneration intentionally records it.
- For every supplied `iterations:N` or `duration:D`, the
  coordinator must keep advancing managers, workers,
  reviewers, testers, validation, integration, or blockers
  until the budget plan's acceptance criteria are met,
  terminal state is reached, the human explicitly pauses or
  stops, a real blocker prevents every safe packet from
  moving, or elapsed wall-clock time exceeds
  `RUN_BUDGET_OVERRUN_EXIT_MINUTES`.
- Pull requests, pushes, and ready-to-review states are
  non-stopping delivery events inside the conductor loop.
  They may be performed whenever a coherent stack is ready,
  and they must be recorded as tick work, but they are not
  the top-line goal and do not end a budgeted invocation
  while the lease remains active and safe work can still
  move.
- Pending PR checks or queued CI are health facts to monitor
  in parallel with the next implementation, review,
  verification, or integration tick. They stop the loop only
  when a concrete failure or service outage blocks every
  safe next packet.
- Reaching `N`, reaching `D`, or reaching both is not enough
  to stop a budgeted invocation when budget-plan acceptance
  criteria remain unmet and safe work can still move. If the
  invocation stops before budget acceptance, the handoff
  must call out unmet acceptance criteria, gate shortfalls,
  tick shortfall, elapsed minutes, active lanes, exact stop
  reason, and exact resume invocation.
- Strip one matching outer quote pair when present.
- Trim surrounding whitespace.
- Reject empty arguments.
- Reject `iterations` values that are missing, zero,
  negative, non-integral, or contain non-digit characters.
- Reject `duration` values that are missing, zero, negative,
  lack a unit, use any unit except `m` or `h`, or contain
  non-digit characters before the unit.
- Reject `numM1s` values that are missing, zero, negative,
  non-integral, or contain non-digit characters.
- Require `plan_path` to identify a file under
  `~/<plan-store>/`, expressed with that `~` prefix or as
  the equivalent absolute path under the current user's
  home directory.
- Deprecated migration compatibility: also accept a
  repo-relative path under `.agents/projects/` in the
  invocation repository for the existing `green()`,
  `greenTick()`, and other wrapper callers until they
  migrate their plans to the central store. Require that
  compatibility path to resolve through the linked store to
  a committed file in the backing
  `<owner>/<project-store>` repository. Never treat the
  invocation repository or its symlink entry as the plan
  store. No new caller may use a project-local plan path.
- Require the file name to end in `.plan.m2.gpt.md` or be
  exactly `plan.m2.gpt.md`.
- Require the file to exist and be readable.
- If a resume argument is present, require the run log for
  that `RUN_ID` to exist and match
  `PLAN_STORE_RELATIVE_PATH`.
- Treat the invocation as standalone. Do not mix unrelated
  user work into the same prompt.
- Supplemental prompt prose is optional. Correct `m2()`
  execution must not depend on prompt reminders outside the
  protocol, the M2 plan entrypoint, and any declared project
  root. Prompt reminders that are necessary for continuation
  must be persisted in the runnable resume prompt record
  described below, not left in chat history.
- `resume:RUN_ID`, `iterations:N`, `duration:D`, and
  `numM1s:M` are the only normal prompt-level execution
  modifiers. Other natural-language text may request pause,
  stop, status, or scope change, but normal build behavior
  belongs in the protocol and plan files.
- The invoked plan's plan-store repository identity and
  repository-relative path (`PLAN_STORE_IDENTITY` and
  `PLAN_STORE_RELATIVE_PATH`) are the source of identity.
  `m2()` must derive the run name, slug, worktree paths,
  branch names, project root, and artifact paths from the
  supplied plan file, not from a host-specific absolute path
  or a hardcoded product plan.

Bounded green tick compatibility:

- Protocol wrappers may declare a bounded compatibility tick
  over an M2 plan. The initial supported wrapper is
  `greenTick()`.
- A bounded compatibility tick is not a normal bare `m2()`
  exit. It may intentionally return after exactly one
  durable conductor tick only when the wrapper protocol says
  so and the run writes a Final Response Gate Record with
  status `green_tick_handoff`.
- The tick must still satisfy the Real Work Tick Contract or
  record a true blocker that prevents every safe selected
  packet from moving.
- The tick must regenerate the runnable resume prompt,
  update the plan resume-prompt pointer when applicable, and
  include the exact next wrapper invocation in
  `resume_invocation`.
- `green_tick_handoff` is valid only for bounded green tick
  wrappers. It is an early-stop violation for normal
  `m2(...)`, `green()`, budgeted invocations, or any wrapper
  that has not explicitly declared bounded tick semantics.
- A changed target selector, newly selected pull request,
  queued CI run, pushed branch, PR update, or green
  confirmation is not a true blocker for a bounded tick.
  Record it and choose the next safe packet or hand off with
  the exact next tick command.

Meaning and scope:

- `m2()` is an orchestration protocol, not a coding
  shortcut.
- When plan validation passes, `m2()` must not ask whether
  to implement, summarize instead of running, or restart
  planning-only discussion. It proceeds into durable
  conductor execution.
- The active invocation repo and worktree are the default
  execution surface. Do not assume a fixed devcontainer
  checkout path, a fixed run directory beside it, or any
  other fixed path.
- The durable MoM control plane defaults to a
  desktop-friendly same-thread conductor mode when the
  invocation environment is already a valid repo and tool
  context.
- Isolation remains a safety tool, not a universal
  prerequisite. Use isolated control, integration, or worker
  worktrees where they materially reduce risk, protect a
  shared checkout, or enable safe parallel edits.
- The coordinator may run directly in a dedicated
  implementation worktree, append durable artifacts there,
  integrate there, validate there, and keep localhost demos
  there when that worktree is the active implementation
  surface.
- For active product work, prefer to keep using the same
  implementation worktree and devcontainer context for
  continuity of tools, localhost demos, caches, and
  artifacts, but cut fresh coding branches from the latest
  `origin/main` whenever the current feature branch has been
  landed, superseded, or has drifted enough that the next
  work wave should start cleanly from main.
- Runnable resume prompts are part of the durable control
  plane. A human should be able to issue only
  `m2(plan_path)` and get the same continuation behavior as
  pasting the latest saved resume prompt by hand.
- The coordinator must not perform feature edits in a shared
  or protected checkout merely because that checkout was the
  invocation surface. In that case, keep the shared checkout
  read-only for bootstrap and move edit-capable work into a
  dedicated implementation, integration, or worker worktree.
- Historical plans under `~/<plan-store>/done/` are
  evidence and must not be rewritten.

Runnable Resume Prompt Contract:

- `RUN_RESUME_PROMPT_PATH=${RUN_ARTIFACT_DIR}/resume-prompt.gpt.md`
  is the canonical runnable continuation prompt for a
  non-terminal run. It is machine-facing and must be
  sufficient for a later conductor to continue without
  relying on chat history.
- `RUN_RESUME_COCKPIT_PATH` remains the human-facing status
  dashboard. It may summarize, link, or quote the runnable
  prompt, but the runnable prompt text lives at
  `RUN_RESUME_PROMPT_PATH`.
- Each project run maintains
  `PLAN_RESUME_PROMPT_POINTER_PATH=${PROJECT_ABS}/state/m2-resume-pointers/${PLAN_IDENTITY_SHA256}.gpt.json`
  when `PROJECT_ROOT` is present, otherwise
  `${HOST_PLAN_STORE_GIT_DIR}/m2-resume-pointers/${PLAN_IDENTITY_SHA256}.gpt.json`.
  The lowercase SHA-256 plan identity keeps this mutable
  pointer isolated from every other plan in the same project
  or canonical plan directory. The pointer records the
  latest compatible resume prompt record for only that exact
  canonical repository-relative plan path.
- A plan may also provide a plan-level default resume
  capsule under the same pointer path before the first
  durable run artifact exists. That capsule must identify
  itself as plan-level state and still include full prompt
  text, worktree, branch, PR, localhost URL, stop policy,
  local-only excludes, current focus, and validation
  artifacts.
- Bare `m2(plan_path)` resolution order is:
  1. parse explicit modifiers; if `resume:RUN_ID` is
     present, use that run and ignore the latest pointer
     except to fill missing resume-prompt fields for the
     same run;
  2. load `PLAN_RESUME_PROMPT_POINTER_PATH` when it exists;
  3. verify `plan_path`, lifecycle compatibility, prompt
     hash, and worktree accessibility;
  4. hydrate `prompt_text` as the effective execution
     prompt;
  5. apply any explicit `iterations:N` or `duration:D` from
     the invocation as invocation-local overrides;
  6. continue the saved run or plan capsule;
  7. if no compatible pointer exists, start a fresh run.
- A saved prompt is compatible only when its plan-store
  identity matches `PLAN_STORE_IDENTITY`, its `plan_path`
  matches `PLAN_STORE_RELATIVE_PATH`, its `plan_blob_id`
  matches `PLAN_SOURCE_BLOB_ID`, its lifecycle is not
  terminal, and its worktree or an equivalent
  environment-derived conductor surface is available. Never
  compare host absolute paths for resume compatibility, and
  never hydrate a run created from different plan bytes at
  the same path.
- Persist `plan_store_identity` as `PLAN_STORE_IDENTITY` and
  persist `plan_path` as `PLAN_STORE_RELATIVE_PATH` in new
  resume pointers, prompts, run logs, and events. Also
  persist `plan_source_commit` and `plan_blob_id`; use the
  blob as the revision compatibility check and the commit as
  the revision-pinned source locator. A host absolute plan
  path may be recorded only as non-identity diagnostic
  context.
- Before hydrating a compatible saved prompt, run a Resume
  Freshness Preflight. Verify the worktree exists, the
  branch exists, the current HEAD and remote relation are
  known, the PR URL is reachable when present, the canonical
  localhost URL is healthy or restartable, listed proof
  artifacts still exist, and local-only excludes remain out
  of the tracked diff.
- If the preflight finds stale or missing state, repair the
  resume capsule and append a `resume_freshness` event
  before counting product ticks. The repair tick is
  increment-eligible only when it directly unblocks a
  blocking product gate.
- Explicit `iterations:N` never permanently rewrites the
  saved tick goal unless a later non-stopping delivery event
  regenerates the resume prompt with that policy on purpose.
- Explicit `duration:D` never permanently rewrites the saved
  wall-clock goal unless a later non-stopping delivery event
  regenerates the resume prompt with that policy on purpose.
- Every pause handoff, non-stopping delivery event, PR
  update, browser-visible validation event, or non-terminal
  final response must regenerate `RUN_RESUME_PROMPT_PATH`
  and update `PLAN_RESUME_PROMPT_POINTER_PATH` before the
  conductor stops.

Product Execution Spine:

- For `execution_intent: implement_product`, the conductor
  must keep this loop near the top of every active tick:
  choose the highest-value blocking gate, implement the
  smallest useful slice, run quick proof, run full proof
  when the slice is browser-visible or risky, commit and
  push coherent work, publish structured PR proof, refresh
  the runnable resume prompt, then continue to the next
  movable gate.
- This spine outranks meeting-like coordination,
  protocol-only cleanup, repeated context rereads, and PR
  watching while safe product work remains.
- Non-stopping delivery events are milestones inside the
  spine. They are not terminal run states unless the real
  terminal criteria are met.
- If a product run has red browser or UX gates, at least one
  visible localhost proof must be produced within each small
  batch of productive UI ticks unless the active packet is
  explicitly non-visual or blocked.

Post-Delivery Continuation Contract:

- Every non-stopping delivery event must immediately produce
  or refresh `RUN_POST_DELIVERY_EVENT_NEXT_PACKET`. Delivery
  events include green validation, commits, pushes, PR
  creation or update, PR comments, CI pass/queue/skip
  classification, screenshot or browser proof, deploy proof,
  and resume prompt or capsule refresh.
- The next packet after a delivery event must be selected in
  this priority order unless the invoked plan supplies a
  stricter order: fix a current-head red or flaky gate;
  continue the next named product lane; add proof coverage
  for recently delivered behavior; improve beta-quality UX
  or product clarity; unblock CI, review, merge, or
  delivery; or discover a new beta-enabling deliverable from
  gates, acceptance rows, PR comments, project docs, code
  inspection, or recent validation artifacts.
- If no named packet remains, the conductor must discover
  and record a new safe product, proof, review, integration,
  or delivery packet before considering a final response.
  "No named packet remains" is not a stop reason by itself.
- A green gate pack, clean PR update, passing CI set, proof
  comment, or refreshed runnable resume prompt is an
  eligibility signal to advance to the next packet. It is
  not proof that the run is complete.

Real Work Priority Contract:

- For `execution_intent: implement_product`, the top-line
  goal is shipped product behavior with working validation,
  not orchestration theater.
- Prefer work in this order unless the plan says otherwise:
  implementation, integration, targeted validation, browser
  evidence, blocker removal, review, delivery hygiene, then
  protocol or cockpit maintenance.
- Once plan validation, initial manager review, and the
  first safe edit scopes exist, the run must spend the
  majority of subsequent ticks on code, tests, integration,
  or browser-validated behavior.
- Support work includes status narration, board grooming,
  repeated file rereads, repeated blocker restatement, PR
  housekeeping without new code or evidence, protocol or
  plan edits, cockpit-only updates, and meeting-like
  coordination. Support work may happen only when the human
  asked for it or when it directly unblocks a concrete
  packet.
- For product runs, edits limited to protocol files, plan
  files, cockpit artifacts, or other run metadata do not
  satisfy product progress unless the human explicitly asked
  for those edits or the run is blocked on missing execution
  guidance.
- Re-reading the same context without a new decision, diff,
  validation result, or blocker resolution is not real work.
- After safe implementation work exists, support-only work
  must not consume more than two consecutive ticks.

Delegated Management Contract:

- `m2()` keeps a durable manager-of-managers shape. The
  conductor owns run safety, priority, integration,
  recovery, and cross-manager arbitration. It is not the
  default place for prolonged packet-level design or
  implementation reasoning when that work can be delegated
  safely.
- After the board exposes two or more independent movable
  domains, packets, or blocker-clearing lanes and
  `RUN_NUM_M1S` is greater than `1`, the conductor must keep
  up to `RUN_NUM_M1S` active M1 manager lanes rather than
  serializing higher-level thinking in the top thread. When
  `RUN_NUM_M1S` is `1`, the conductor may run one M1 lane
  deeply while still using lower-level SWE, verification, or
  evidence fanout inside that lane when safe.
- The conductor should prefer to spend its own deep thinking
  budget on:
  - cross-manager conflicts;
  - lease and integration ordering;
  - review findings;
  - blocker triage that affects multiple packets;
  - acceptance and delivery decisions.
- Each M1 manager lane runs the `m1()` protocol
  (`references/m1.protocol.md`); see it for how a
  lane shapes packets, owns its file and validation scope,
  fans lower-level execution out to SWEs, keeps per-worker
  supervision rows, and reaches an exit state.
- Parallel fanout is the default execution shape, not a rare
  escalation. Whenever safe parallel work exists, the
  conductor should keep M1 managers and their lower-level
  SWEs active concurrently instead of batching one lane at a
  time.
- Fanout Trigger Rule: when two or more independent gate,
  write, validation, evidence, or collaboration lanes can
  move safely, adapter capacity exists, and `RUN_NUM_M1S` is
  greater than `1`, a counted conductor tick must either
  dispatch or resume up to `RUN_NUM_M1S` unique M1 lanes, or
  record the specific lease, risk, capability, or dependency
  blocker that prevents the requested fanout. The conductor
  may keep the immediate integration-critical lane locally
  only when the event also records what other safe lane is
  moving in parallel.
- How a lane separates code generation from companion
  collaboration work, and how it pairs code with browser and
  screenshot evidence, is owned by the `m1()` protocol
  (`references/m1.protocol.md`).
- Conductor-local implementation is reserved for low-risk
  sole-owner work, integration glue, emergency unblockers,
  or cases where no safe manager or worker path exists in
  the current tick.
- If the conductor notices itself repeating packet-level
  exploration that an M1 manager could own for two
  consecutive productive ticks, it must dispatch, resume, or
  redirect that M1 before continuing locally.
- If an M1 manager spends two consecutive active ticks
  without dispatching a SWE, integrating worker output, or
  recording a concrete blocker, the conductor must
  interrupt, rescope, or replace that M1.
- If an M1 manager has one active SWE lane but still has
  another safe disjoint collaboration, validation, or code
  lane available, the conductor should push that manager to
  split again before reclaiming that reasoning centrally.

Active Agent Supervision Cadence Contract:

- Active M1 managers, SWEs, testers, verification workers,
  reviewers, and delivery workers are live production
  capacity. The conductor must treat idle agents as a
  throughput defect, not as background decoration.
- During an active run, every conductor tick must include a
  non-blocking supervision pass over known active agents:
  poll finished agents whose output may unblock work,
  redirect idle or stale agents, close agents that are no
  longer useful, and record any agent that cannot be
  contacted or safely reused.
- The supervision pass is an active continuation prompt, not
  a passive status check. Each active M1 must be asked for
  current status, tangible deliverable, blocker, next
  action, and whether it should continue, split work, hand
  off, or close.
- A running agent should always own a tangible deliverable:
  code, tests, browser evidence, CI triage, online or
  internal research distilled into a design note, meeting
  log, PRD, review bundle, command transcript, or concrete
  blocker report with next action. Pure waiting, repeated
  narration, and unbounded deliberation are not acceptable
  manager states.
- If an M1 manager or SWE returns useful results, the
  conductor must either integrate or review the result,
  immediately assign the next deliverable, or close the
  agent with the reason recorded. Completed agents must not
  remain idle across multiple ticks when safe follow-on work
  exists.
- Stale, complete, duplicate, or no-longer-useful lanes must
  be closed or reassigned during the same supervision pass
  that detects them so `RUN_NUM_M1S` capacity reflects lanes
  that can still produce meaningful code, evidence, design
  notes, meeting logs, blocker reports, or delivery proof.
- Long-running lint, build, test, browser validation,
  screenshot capture, CI polling, and PR-health monitoring
  should be delegated to verification, evidence, or delivery
  lanes whenever the adapter and workspace allow it. The top
  conductor thread should launch, monitor, and interpret
  those runs; it should not spend its main reasoning window
  simply waiting for them while managers could be moving.
- If a long-running command is already occupying the top
  thread, the conductor must keep managing around it: poll
  agents, redirect work, update protocol or plan blockers,
  prepare integration decisions, and dispatch disjoint work.
  Future equivalent commands should be assigned to a
  background verification/evidence worker unless the
  conductor records why same-thread execution is necessary.
- Agent check cadence must be explicit in durable state.
  Record the last supervision action, owner, deliverable,
  status, and next check for each active lane in the event
  log or any materialized board/cockpit view. For long runs,
  no active lane should go more than two productive ticks
  without either a poll, redirect, deliverable update, or
  recorded blocker.
- The per-worker supervision rows inside a lane are owned by
  the `m1()` protocol
  (`references/m1.protocol.md`). The conductor's
  duty here is the cross-lane supervision pass, not the
  per-worker rows inside any single lane.

PR Portfolio Pressure Contract:

- Open pull requests are review capacity, not only delivery
  artifacts. `m2()` should keep the active PR portfolio
  small enough that reviewers and the conductor can still
  understand the system state.
- The default active-review target is one to three open PRs
  per product program. This is a soft metric, not a product
  blocker: it should guide consolidation and sequencing, but
  it must not stop urgent hotfixes or safe product progress.
- Each active M1 manager has at most one open PR slot by
  default. The PR slot may receive many pushed waves from
  that M1, but the M1 should not scatter unrelated branches
  into multiple simultaneously open review surfaces.
- When `RUN_NUM_M1S` is greater than the active-review
  target, the Delivery Manager should group lanes into a
  small number of review surfaces, such as depth/stability,
  breadth/capability, and evidence/delivery, rather than
  opening one disjoint PR for every active lane.
- Before opening a new PR, the conductor must check whether
  the change belongs in an existing M1 PR slot, can be
  stacked on a named parent PR, or should wait until an
  existing slot lands or is superseded. The non-stopping
  delivery event must record that decision.
- If multiple disjoint PRs are already open, prefer safe
  consolidation: merge ready lower-risk PRs first, rebase or
  retarget dependent PRs onto the landed base, move
  compatible follow-up commits into the current active slot,
  and close superseded PRs with a link to the surviving
  review surface.
- A new disjoint PR is justified when the write scope,
  review owner, deployment risk, or dependency order would
  make consolidation unsafe or materially slower. Record the
  reason and the intended merge order.
- PR count pressure is delivery/meta health data. It is not
  increment-eligible by itself while product gates are red,
  but reducing avoidable open PR sprawl can support
  `delivery_meta` gates when paired with real integration,
  review, or merge-order work.

Local Lint Discipline Contract:

- Local lint is a pre-push discipline, not a CI
  afterthought. GitHub lint workflows must not be the first
  formatter, whitespace, static, or syntax pass for a pushed
  slice.
- Auto-generated lint PRs are cleanup pressure, not an
  acceptable normal delivery path. If a local slice would
  predictably cause a lint bot or connector to open a
  formatting-only PR, the conductor must treat that as a
  local process failure, run the needed local lint or syntax
  checks, inspect any rewrites, and push only after the
  branch itself is lint-clean.
- Before every commit, run `git diff --check` and the
  smallest relevant local lint, static, syntax, or schema
  checks for the changed files. For JavaScript tooling,
  include `node --check` when repo lint does not parse the
  file. For structured run state, parse or schema-check the
  changed record before committing.
- Before every push, confirm the committed slice has passed
  scoped repo lint for all changed non-deleted paths when a
  scoped lint command exists. If the repo lint tool reports
  a path as unsupported, pair it with the strongest local
  syntax/static check available for that file type, such as
  `node --check` for JavaScript or the relevant parser for a
  structured artifact. Record the exact lint commands,
  unsupported-path fallbacks, and results in the
  non-stopping delivery event.
- Run broad repo lint, using the repository's documented
  lint command, before pushing when the slice has repo-wide
  effect or formatting risk:
  rebases, merge-conflict resolution, BUILD/tooling changes,
  generated-output changes, mechanical C++ formatting
  changes, protocol/schema changes that alter validation
  shape, or any edit whose affected lint scope is ambiguous.
- Broad repo lint must be run from a clean tracked scope
  whenever possible. Before invoking it, move, ignore, or
  otherwise exclude local-only artifacts such as
  `.agents/local/`, Playwright browser installs,
  `node_modules/`, Bazel outputs, screenshots, and report
  caches from the lint input. If the repo lint command
  cannot exclude those paths, prefer a clean worktree, a
  tracked-file lint mode, or scoped lint plus a recorded
  broad-lint blocker over formatting proof artifacts and
  unrelated local-only files.
- If lint rewrites files, treat those rewrites as local
  implementation output: inspect the diff, rerun the
  relevant lint/static/test gate, include the rewrite in the
  same coherent commit when appropriate, and do not push
  until the post-rewrite lint state is clean.
- If broad lint rewrites unrelated tracked files outside the
  owned slice, inspect the diff and restore those unrelated
  rewrites before pushing unless the human explicitly
  expands the write scope.
- Long-running lint may be delegated to a Verification,
  Evidence, or Delivery lane, but the conductor must receive
  and record the pass/fail result before pushing or updating
  a PR proof comment for the slice.
- A passing lint run is delivery hygiene and event evidence.
  It is not, by itself, product-gate progress and must not
  end a budgeted `m2()` invocation while safe product work
  remains.

Auto-Lint PR Prevention Contract:

- Auto-generated lint PRs against the active work branch are
  a hard local hygiene failure, not a review artifact to
  tolerate or merge later.
- Before every push to a product branch, the conductor must
  query for open auto-generated PRs targeting the active
  branch:

  ```sh
  ACTIVE_BRANCH="$(git branch --show-current)"
  gh pr list --state open --label auto-generated \
    --search "base:${ACTIVE_BRANCH}"
  ```

- The query must be clean before pushing. If it returns one
  or more PRs, stop the push path, inspect each owned diff
  with `gh pr diff <number>`, apply the
  equivalent lint or formatting change locally in the active
  branch when it is in scope, rerun the relevant scoped or
  broad lint gate, and commit the owned fix before pushing.
- Do not merge auto-generated lint PRs into product branches
  as the normal remediation. The preferred remediation is an
  owned local commit on the active branch, followed by
  closing the auto-generated PR as superseded once the
  branch contains the equivalent diff.
- Because auto-generated lint PRs can be caused by
  branch-wide files outside the immediately touched packet,
  scoped lint is necessary but not sufficient for long-lived
  product branches. After rebases, conflict resolution,
  broad mechanical edits, or repeated auto-generated PR
  churn, run broad repo lint or a tracked-file equivalent
  before the next push.
- Every non-stopping delivery event and PR proof comment
  must record `auto_generated_pr_query_clean`, the active
  branch, the exact query command or equivalent, the number
  of matching PRs, and any supersession actions taken.
- Auto-generated PRs targeting stale branches that have
  already landed or been superseded must be closed with a
  comment naming the landing PR, merge commit, and surviving
  branch. Do not close auto-generated PRs for unrelated
  active branches unless that branch is explicitly in scope.

PR Stack Readiness And Merge Backpressure Contract:

- PR readiness is active Delivery work, not a reason to stop
  the conductor. When a branch is pushed or a PR is opened,
  updated, marked ready, reviewed, queued, or considered
  mergeable, write or refresh a PR Stack Readiness Record.
- Before claiming a PR or stack is ready to merge, inspect
  branch sync against `origin/main`, the open PR set, commit
  count between base and head, review state, unresolved
  conversations, required checks, auto-generated PR sentinel
  status, mergeability, and repository-supported merge
  strategies.
- Keep review surfaces small enough for the repository's
  merge path. Prefer coherent PRs with one reviewed product
  slice each. If a long run creates a large linear stack,
  Delivery must decide whether to merge parent PRs, restack
  children, or collapse an owned branch before it becomes a
  service-side merge blocker.
- If the repository's server-side rebase or normal merge
  path fails for a large owned linear stack after checks and
  review are otherwise acceptable, recover without losing
  work: create a backup branch at the current head; confirm
  no unrelated user changes are in the branch; reset the
  owned branch index to `origin/main` with the same final
  tree preserved; recommit that final tree as one coherent
  PR commit or the smallest repo-compatible commit set;
  force-push with lease; rerun the sentinel, lint, checks,
  and mergeability probes; then retry the repo-compatible
  merge path.
- Do not collapse or force-push branches that contain
  unrelated user work, unreviewed external commits, or
  ambiguous ownership. In that case, record the exact
  blocker and keep safe non-overlapping packets moving.
- Merge waiting, queued checks, and review latency are
  backpressure signals. They may redirect new work to a
  fresh branch from latest `origin/main`, to stacked child
  PRs, or to evidence/validation packets, but they do not
  end a budgeted run while safe work remains.

Prompt Minimalism Contract:

- A bare valid `m2(plan_path)` invocation must be enough to
  run the plan.
- If a reminder is required for normal execution, durable
  conductor behavior, project loading, worker dispatch,
  reviews, cockpit artifacts, validation, evidence, terminal
  state, or handoff, that reminder belongs in this protocol,
  the M2 plan entrypoint, or the declared project root.
- Managers, workers, testers, and reviewers must not rely on
  hidden or previous chat prose for their instructions. They
  must receive explicit project files, packet rows, manager
  files, subproject files, acceptance rows, and artifact
  paths.
- If the plan can only be executed correctly when the user
  repeats build instructions in the prompt, validation must
  fail and report the missing protocol or plan requirement.

Literal m2 Autonomy Contract:

- Treat a valid literal invocation such as `m2(plan_path)`,
  `m2(plan_path, duration:24h, numM1s:4)`, or the same shape
  with explicit `resume:`, `iterations:`, or `duration:`
  parameters as an instruction to run the durable conductor,
  not as a request for a plan summary.
- The invocation must be self-sufficient after the ellipses
  or parameters are expanded. Normal autonomous behavior
  must come from this protocol, the invoked plan, its
  project file network, runnable resume prompt records, and
  canonical run events, not from hidden chat history or
  repeated human reminders.
- On every start or resume, the conductor must complete an
  autonomy hydration pulse before deciding the next action:
  parse invocation modifiers; load the plan and project
  manifest; resolve runnable resume prompt state; reconcile
  git status, branch, active PRs, checks, worktrees,
  localhost/demo state, active agents, process pressure,
  local-only artifact pressure, and pending validation
  evidence; then write an Autonomy Health Event.
- After hydration, run the autonomy loop until the Final
  Response Gate returns a non-continue status. Each loop
  pass must select one or more next safe packets, attempt
  fanOut when capacity exists, keep parent critical-path
  work moving, integrate reviewed output, run the relevant
  lint/validation/evidence gates, append canonical events,
  refresh the runnable resume prompt when continuation state
  changes, and then rescan.
- A delivery event is a checkpoint inside that loop. After a
  commit, push, PR update, proof comment, screenshot, green
  validation, queued CI observation, or merge-readiness
  probe, record the event, link any integrated fanOut
  output, refresh the next packet selection, and continue
  unless the Final Response Gate says otherwise.
- If local tool/process pressure rises, such as too many
  open shell or unified exec sessions, the conductor must
  switch lanes before stopping: reuse existing sessions,
  close or ignore completed sessions when the environment
  permits, avoid starting duplicate dev servers or idle
  long-running commands, delegate or queue waits to
  Verification/Evidence/Delivery lanes, and keep code or
  review work moving in scopes that do not require more
  long-lived processes. Record `tool_capacity` only when
  process pressure blocks every safe next packet.
- Idle M1 capacity is a signal to rebalance, not to final
  respond. Reassign idle lanes to safe product work,
  verification, evidence, CI triage, PR-stack readiness,
  lint cleanup, or fanOut-compatible packets before
  considering a pause.
- Missing optional cockpit markdown, stale human-facing
  summaries, queued CI, pending remote review, process
  pressure, or a just-opened PR are not stop reasons by
  themselves. They are health facts that must be recorded
  and worked around while any safe packet can move.
- Before any final response, the conductor must write a
  Final Response Gate Record. If that record returns
  `continue_required`, append an early-stop violation event
  if a final response was attempted, select the next packet,
  and continue the loop.

Plan Identity And Source Contract:

- Treat the plan file at `PLAN_SOURCE_PATH` in its plan
  store as the source of truth for identity and bootstrap.
  Never copy it into an active, control, integration, or
  worker worktree.
- Parse YAML front matter from `PLAN_SOURCE_PATH` before
  creating or locating run worktrees.
- Derive `PLAN_NAME` from front matter `name`.
- If `PLAN_NAME` is empty, derive it from `PLAN_BASENAME` by
  removing a leading `YYYY-MM-DD-` prefix and the trailing
  `.plan...md` suffix.
- Derive `PLAN_SLUG` from `PLAN_NAME` by lowercasing,
  replacing non-alphanumeric runs with `-`, trimming leading
  and trailing `-`, and shortening to a safe branch-name
  length.
- Derive `WORKTREE_SLUG=m2-${PLAN_SLUG}-${RUN_ID}`.
- Derive every run worktree and branch from `WORKTREE_SLUG`,
  `PLAN_SLUG`, and `RUN_ID`.
- Before durable conductor validation, require
  `PLAN_SOURCE_PATH` to remain readable from the conductor
  execution surface.
- If the plan declares `project_root`, seed that
  repo-relative project file network from the active
  invocation repo into `CONTROL_WORKTREE` when the conductor
  worktree is different and required files are missing or
  stale. Do not seed unrelated files.
- Do not special-case any product, project root, or fixed M2
  plan entrypoint path in this protocol.

Execution Mode And Isolation Contract:

- `m2()` supports two conductor modes:
  - `same_thread`: the default desktop-friendly mode. Run
    the conductor directly in the active repo worktree when
    that worktree is already a valid coordination and
    implementation surface.
  - `isolated_control`: create or reuse a dedicated control
    worktree when the active checkout is shared or
    protected, when risky integration or validation needs a
    cleaner surface, when unrelated dirty state overlaps the
    run scope, when the human requests isolation, or when
    the plan explicitly requires it.
- Bootstrap relocation is optional. If relocation is used,
  it is setup work only and must not consume an iteration.
- The protocol must clearly separate what must be isolated
  from what may run directly in the active thread:
  - must be isolated when risk or ownership requires it:
    edit-capable workers with overlapping write scopes,
    risky experiments, deploys, shared-environment mutation,
    or integrations that would dirty a shared or protected
    checkout;
  - may run directly in the active thread and worktree: plan
    validation, canonical event append, board and handoff
    repair, prompt assembly, read-only exploration, diff
    review, targeted validation, browser smoke, localhost
    demos, and same-thread implementation or integration
    inside a dedicated implementation worktree.
- `same_thread` does not waive worker isolation. When more
  than one edit-capable stream needs branch or file
  isolation, the conductor must still create worker
  worktrees under `RUN_ROOT`.
- `isolated_control` must record the control worktree,
  integration worktree, worker worktree root, and any
  relevant devcontainer proof in the run artifacts. A run in
  `same_thread` mode may record the same environment facts,
  but missing optional proof markdown must not block useful
  work when the canonical event log already exists.
- If the active checkout is the shared primary checkout on a
  protected branch, the conductor may use it for read-only
  bootstrap, status, and dispatch, but not for feature edits
  or risky validation. Move those steps into a dedicated
  implementation, integration, or worker worktree.
- `m2(plan_path, resume:RUN_ID)` must resume using the
  recorded `CONDUCTOR_MODE` when that environment still
  exists. If the old mode is unavailable, recover from the
  canonical event log into the safest compatible mode and
  record the switch explicitly.
- Missing or stale optional cockpit markdown is never by
  itself a blocker. Rebuild it from `RUN_EVENTS_PATH`.

Execution Adapter Contract:

- The protocol must know how work is actually carried out. A
  valid run needs concrete adapter operations for:
  - bootstrap control worktree;
  - create worktree;
  - enter devcontainer;
  - re-invoke conductor;
  - start manager;
  - start worker;
  - start tester;
  - start reviewer;
  - wait for progress;
  - collect output;
  - capture diff;
  - run review;
  - integrate accepted diff;
  - commit integrated changes;
  - push branch;
  - open pull request;
  - update pull request;
  - poll and record pull request checks;
  - close worker;
  - retry packet;
  - resume run.
- Every active manager, worker, tester, reviewer, or
  worktree must have:
  - stable adapter id;
  - owner packet;
  - owner manager;
  - lifecycle state;
  - assigned model and effort;
  - output artifact path;
  - worktree path when applicable;
  - retry count;
  - last heartbeat tick;
  - close or quarantine state.
- A conductor tick may dispatch work only through the
  adapter operation recorded in `events.gpt.jsonl`.
- If the current tool environment lacks a needed adapter
  operation, the coordinator must mark the affected packet
  `blocked` or `paused_for_capacity` with exact missing
  capability and resume path.

Worktree And Integration Contract:

- Run roots live under the environment-derived
  `${RUNS_ROOT}/${WORKTREE_SLUG}`.
- In `same_thread` mode, `CONTROL_WORKTREE` is the active
  worktree and may also be `INTEGRATION_WORKTREE` when that
  worktree is already the designated implementation or
  integration surface.
- In `isolated_control` mode, control worktrees live at
  `${RUN_ROOT}/control` and integration worktrees live at
  `${RUN_ROOT}/integration`.
- Worker worktree paths use
  `${WORKER_WORKTREE_ROOT}/<packet-id>/` when a packet needs
  branch or file isolation. A packet may also reuse an
  existing dedicated implementation worktree when the board
  records that ownership explicitly.
- Worker branch names use
  `m2/<RUN_ID>/<PLAN_SLUG>/workers/<packet-id>`.
- Diff artifacts normally live under
  `${RUN_ARTIFACT_DIR}/diffs/<packet-id>.patch` when they
  are captured. Direct worker commits or same-thread
  integration commits are also valid inputs when the event
  log records their source branch, commit SHA, and changed
  paths. Worker summaries alone are never integration input.
- Run logs, canonical events, board files, required handoff
  artifacts, and any materialized cockpit views are written
  under `${REPO_ROOT}/.agents/logs/` inside whichever
  worktree currently owns the conductor surface.
- Shared-file packets integrate in file lease order or as
  explicit stacked patches recorded on the board.
- Conflict resolution requires a written reconciliation
  artifact with conflict path, owning managers, accepted
  order, rejected alternative, and reviewer.
- The last known good point is recorded after each passing
  targeted validation run as commit SHA, validation command,
  and evidence artifact path.
- Failed worktrees are quarantined under the same run until
  Delivery records abandon, retry, or mine-for-partial-patch
  decision.
- Cleanup is a Delivery action after terminal handoff; it
  must not remove worktrees with unintegrated diffs,
  unresolved findings, or missing evidence records.

Scheduling Policy:

- Default active capacity:
  - managers: 4;
  - edit-capable workers: 6;
  - verification workers: 3;
  - reviewers: 3.
- Plans may choose lower limits. Higher limits require
  Delivery and Uber TL acceptance.
- Prioritize critical path packets, interface lock packets,
  evidence blockers, and integration blockers before
  optional parallel work.
- Use available safe capacity aggressively. When one packet
  can support both code generation and companion
  collaboration artifacts in disjoint scopes, prefer running
  both rather than finishing one before starting the other.
- Idle capacity may run read-only exploration, test design,
  evidence indexing, or review preparation.
- Retry budget is two attempts per packet before split,
  scope reduction, or human escalation.
- During every tick, the coordinator must scan the full
  board for safe work across all managers before deciding to
  pause. If active capacity is idle and at least one
  non-terminal packet can safely move, the tick must
  dispatch, resume, collect, review, integrate, validate, or
  unblock that packet.
- Completing one packet, one diff, one review, or one
  validation stack is not by itself a pause condition when
  `RUN_ITERATION_GOAL` is `unbounded` or
  `RUN_ITERATIONS_USED < RUN_ITERATION_GOAL`, and another
  safe workstream exists.
- Opening, updating, or pushing a pull request is likewise
  not a pause condition. Delivery may create a chain of PRs
  as reviewed slices become coherent, then immediately
  continue scanning the board for the next safe manager,
  worker, reviewer, tester, validation, or integration
  action.
- If the coordinator leaves capacity idle while safe packets
  remain, the tick event must record the reason, such as a
  file lease dependency, adapter gap, missing context, risk
  boundary, or deliberately chosen critical-path
  serialization.
- Enter `paused_for_capacity` when no safe packet can move
  without more agent capacity, adapter capability, worktree
  capacity, or human decision.

Spark fanOut Codegen Contract:

- At run startup, after every non-stopping delivery event,
  and whenever an M1 lane has idle safe capacity, the
  conductor must attempt `fanOut(..., numWorkers=auto)` for
  bounded code, test, validator, evidence, design-note, or
  review packets that can move in disjoint scopes.
- `fanOut()` is a worker accelerator under active M1
  ownership, not a replacement for M1 responsibility. The M1
  remains accountable for packet choice, file leases,
  integration review, lint, validation, proof, and next
  packet selection.
- Code-editing fanOut workers default to
  `gpt-5.3-codex-spark`. Each worker prompt must include a
  bounded ownership scope, expected patch shape,
  changed-path reporting requirement, validation command,
  lint requirement, and explicit instruction not to revert
  other workers' edits.
- fanOut results are never integrated automatically. The
  conductor or owning M1 must inspect the returned changed
  paths, reconcile leases, apply or reject the patch
  intentionally, run local lint/validation, and record the
  integration decision.
- Respect the normal capacity caps unless an invocation or
  accepted plan explicitly raises them: at most 6
  edit-capable fanOut workers, 3 verification fanOut
  workers, and 12 total fanOut workers active for one fanOut
  event.
- For shared hot files, use file-level leases when possible
  and function-level leases when necessary. If edit leases
  would conflict, fan out validators, browser probes,
  focused tests, design notes, or evidence capture instead
  of competing edits.
- If an M1 has idle capacity but no fanOut launch is safe,
  the tick record must name the concrete blocker:
  `file_lease_conflict`, `shared_hot_file`,
  `missing_context`, `validation_dependency`,
  `risk_boundary`, `tool_capacity`, or another equally
  specific reason.
- A green validation, pushed commit, PR update, proof
  comment, or queued CI result is a non-stopping delivery
  event. After recording it, the conductor must rescan for
  fanOut opportunities before considering any pause or final
  response.

CI And Backpressure Handling:

- Treat queued CI, pending PR checks, merge queues, remote
  scheduler delay, and external review wait as monitorable
  health facts, not automatic stop conditions.
- A queued or pending check blocks only the packet, review,
  or delivery action that depends on that exact result,
  unless the same condition makes every safe next packet
  unsafe to move.
- While some packets wait on CI, the conductor must continue
  scanning for other safe implementation, integration,
  validation, review, or blocker-removal work in the same
  run.
- Waiting on checks is a legitimate tick outcome only when
  the event also records why no safer local progress was
  available in that tick.
- Non-stopping delivery events, ready-for-review states, and
  in-flight PR chains are part of the loop's health picture.
  They are not terminal, not completion, and not pause
  conditions by themselves.

Derived values:

- `INVOCATION_CWD=$(pwd)` before any relocation.
- `INVOCATION_GIT_ROOT=$(git rev-parse --show-toplevel)`.
- `INVOCATION_BRANCH=$(git branch --show-current)`.
- `INVOCATION_HEAD=$(git rev-parse HEAD)`.
- `ACTIVE_REPO_ROOT=${INVOCATION_GIT_ROOT}`.
- `ACTIVE_WORKTREE=${ACTIVE_REPO_ROOT}`.
- `HOST_PLAN_STORE_DIR`: the physical worktree root of the
  repository that owns the plan bytes, resolved through the
  agent's host execution surface. This is the canonical
  `~/<plan-store>` checkout for a central-store plan. For a
  deprecated path under `.agents/projects/`, resolve the
  compatibility symlink first and use the backing
  `<owner>/<project-store>` worktree root. Never use
  `INVOCATION_GIT_ROOT` merely because the logical path
  begins there.
- `HOST_PLAN_STORE_GIT_DIR`: the absolute Git directory for
  `HOST_PLAN_STORE_DIR`, resolved through the same host
  execution surface. Mutable plan-level resume pointers live
  here rather than dirtying the canonical checkout.
- `PLAN_PATH`: normalized absolute logical host path
  accepted from the invocation, resolved before starting or
  entering a devcontainer and retained as host-only state.
- `PLAN_SOURCE_PATH`: normalized physical host path after
  resolving every symlink component in `PLAN_PATH`. Require
  it to remain inside `HOST_PLAN_STORE_DIR`.
- `PLAN_STORE_IDENTITY`: `<owner>/<plan-store>` for a
  central-store plan and `<owner>/<project-store>` for a
  deprecated project-local plan under `.agents/projects/`.
  Prove the selected backing repository has that identity
  and fail closed if it cannot be proved.
- `PLAN_STORE_RELATIVE_PATH`: the forward-slash
  repository-relative path from `HOST_PLAN_STORE_DIR` to
  `PLAN_SOURCE_PATH`. A compatibility plan therefore records
  its path inside `<owner>/<project-store>`, such as
  `<repository>/...`, not the invocation repository's
  `.agents/projects/...` symlink path.
- `PLAN_IDENTITY_SHA256`: lowercase SHA-256 of the exact
  UTF-8 bytes of `PLAN_STORE_IDENTITY`, one newline, and
  `PLAN_STORE_RELATIVE_PATH`.
- `PLAN_SOURCE_COMMIT`: exact `HOST_PLAN_STORE_DIR` commit
  at which the current plan bytes are observed
- `PLAN_SOURCE_BLOB_ID`: exact Git blob object ID for
  `PLAN_STORE_RELATIVE_PATH` at `PLAN_SOURCE_COMMIT`;
  require the worktree bytes to hash to this object before
  parsing
- `PLAN_BASENAME=$(basename "${PLAN_PATH}")`.
- `PLAN_NAME`: front matter `name` from `PLAN_SOURCE_PATH`,
  falling back to `PLAN_BASENAME` with date prefix and plan
  suffix removed.
- `PLAN_SLUG`: lowercase kebab-case slug from `PLAN_NAME`
  with non-alphanumeric runs collapsed to `-`, trimmed, and
  shortened to a safe branch-name length.
- `EXECUTION_INTENT`: `execution_intent` front matter value
  when present, otherwise `execute_plan`.
- `RUN_ID`: generated as UTC timestamp `YYYYMMDDTHHMMSSZ` on
  start, or parsed from the resume argument on resume.
- `RUN_MODE`: `start` when no resume argument is present,
  otherwise `resume`.
- `RUN_ITERATION_GOAL`: parsed from `iterations:N` when
  present, otherwise `unbounded`.
- `RUN_WALL_CLOCK_GOAL_MINUTES`: parsed and normalized from
  `duration:D` when present, otherwise `unbounded`.
- `RUN_TICK_HOUR_RATIO=1000`, the canonical budget-planning
  ratio. One hour of budgeted m2 work maps to 1000
  increment-eligible ticks.
- `RUN_BUDGET_SLICE_TICKS=250`.
- `RUN_BUDGET_SLICE_MINUTES=15`.
- `RUN_BUDGET_TICKS`: `RUN_ITERATION_GOAL` when present,
  otherwise `null`.
- `RUN_BUDGET_MINUTES`: `RUN_WALL_CLOCK_GOAL_MINUTES` when
  present, otherwise `null`.
- `RUN_EFFECTIVE_BUDGET_TICKS`: when both explicit budget
  inputs are present, the maximum of `RUN_BUDGET_TICKS` and
  `RUN_BUDGET_MINUTES * 1000 / 60`; when only one is
  present, that value or its tick equivalent; otherwise
  `unbounded`.
- `RUN_EFFECTIVE_BUDGET_MINUTES`: when both explicit budget
  inputs are present, the maximum of `RUN_BUDGET_MINUTES`
  and `RUN_BUDGET_TICKS * 60 / 1000`; when only one is
  present, that value or its minute equivalent; otherwise
  `unbounded`.
- `RUN_BUDGET_SLICE_COUNT`: for budgeted invocations,
  `ceil(max(RUN_EFFECTIVE_BUDGET_TICKS / 250, RUN_EFFECTIVE_BUDGET_MINUTES / 15))`;
  otherwise `0`.
- `RUN_BUDGET_OVERRUN_EXIT_MINUTES`: for budgeted
  invocations, `RUN_EFFECTIVE_BUDGET_MINUTES * 1.10`.
- `RUN_BUDGET_ACCEPTANCE_STATUS`: `not_planned` before the
  startup budget plan exists, then `open`, `met`, `blocked`,
  or `overrun`.
- `RUN_NUM_M1S`: parsed from `numM1s:M` when present,
  otherwise `1`. It is the requested number of parallel M1
  manager-of-IC lanes for this invocation. Each active M1
  lane must have a unique lane role, gate family,
  customer/user journey, or evidence scope. The conductor
  may run fewer only when safe lane count, file leases,
  dependency order, validation capacity, or adapter capacity
  requires it, and must record that reason.
- `RUN_AGGREGATE_M1_TICKS`: `null` by default. Set to a
  positive integer only when the human or plan capsule
  explicitly states that the tick budget is aggregate M1
  lane work across `RUN_NUM_M1S` lanes. For example, the
  explicit statement
  `16000 ticks = 4 M1 lanes * 4 wall-clock hours * 1000 ticks/hour`
  sets `RUN_AGGREGATE_M1_TICKS=16000`.
- `RUN_PER_LANE_TICKS`: `null` unless
  `RUN_AGGREGATE_M1_TICKS` is set. When set, it equals
  `RUN_AGGREGATE_M1_TICKS / RUN_NUM_M1S` and must be
  recorded per lane in the budget plan. If the aggregate
  value is not evenly divisible by `RUN_NUM_M1S`, record the
  exact distribution in `lane_plan` instead of rounding
  silently.
- `RUN_INVOCATION_STARTED_AT_UTC`: UTC timestamp captured
  immediately after invocation parsing and before resume/run
  setup work begins.
- `RUN_WALL_CLOCK_ELAPSED_MINUTES`: elapsed wall-clock
  minutes since `RUN_INVOCATION_STARTED_AT_UTC`, rounded
  down for progress displays and compared using exact
  elapsed time for stop decisions.
- `RUN_ITERATION_LIMIT`: deprecated compatibility alias for
  old run logs and cockpit artifacts. New protocol text,
  prompts, and artifacts must write `RUN_ITERATION_GOAL`.
- `RUN_ITERATIONS_USED`: number of durable conductor ticks
  completed by the current invocation that are also
  increment-eligible under `Real Work Tick Contract`.
  Initialize to `0` after initial run setup and before the
  first durable conductor tick. Increment only after an
  increment-eligible tick appends its canonical event. This
  is the invocation-local loop counter. In non-budgeted
  compatibility runs, a positive `RUN_ITERATION_GOAL` is the
  compatibility target. In budgeted runs, it contributes to
  `RUN_EFFECTIVE_BUDGET_*`; the stop decision is governed by
  `Budget Exit Contract`.
- When `RUN_WALL_CLOCK_GOAL_MINUTES` is a positive integer,
  the conductor must continue after every tick or
  non-stopping delivery event while elapsed wall-clock time
  is less than that goal in non-budgeted compatibility runs.
  In budgeted runs, it contributes to
  `RUN_EFFECTIVE_BUDGET_*`; the stop decision is governed by
  `Budget Exit Contract`.
- When both `RUN_ITERATION_GOAL` and
  `RUN_WALL_CLOCK_GOAL_MINUTES` are positive integers, the
  supplied values define the effective budget. Budget-plan
  acceptance, not mere counter/time satisfaction, is the
  primary exit target.
- `RUN_ITERATION_STOP_REASON`: empty until the invocation
  stops. Before any non-terminal handoff, set it to one of
  `iteration_goal_reached`, `duration_goal_reached`,
  `iteration_and_duration_goals_reached`, `terminal`,
  `human_pause`, `human_stop`, `no_safe_packet_can_move`,
  `adapter_capability_blocker`, `tool_or_context_limit`,
  `external_service_blocker`, `p0_human_decision`,
  `budget_acceptance_met`, or `budget_overrun_exit`.
  `iteration_limit_reached` may appear only in old run logs
  and should be interpreted as `iteration_goal_reached`. The
  `iteration_*` and `duration_*` reasons are non-budgeted
  compatibility reasons only; any invocation with
  `iterations:N`, `duration:D`, or both is governed by
  `Budget Lease Contract` and `Final Response Gate` instead.
  `ready_review_checkpoint_pushed` and similar PR-centered
  stop reasons are invalid legacy labels unless paired with

Compatibility And Migration:

- Invocation syntax remains backward-compatible and now
  accepts an optional wall-clock modifier:
  `m2(plan_path[, resume:RUN_ID][, iterations:N][, duration:D])`.
- `RUN_ITERATION_LIMIT` remains a deprecated compatibility
  alias for older run logs and cockpit views. New artifacts
  should write `RUN_ITERATION_GOAL`.
- Older runs that recorded fixed-path worktrees or
  `main_worktree` fields remain readable. On resume, prefer
  `RUN_EVENTS_PATH` plus the current environment-derived
  paths over the old fixed path literals.
- Existing plans that still use the legacy headings
  `Operator Cockpit Requirement` and `Artifacts And Status`
  remain valid. New plans should prefer
  `Durable State And Handoff`.
- If an older run has only markdown cockpit artifacts and no
  canonical `RUN_EVENTS_PATH`, resume requires an explicit
  human recovery decision.

Acceptance-First Planning Contract:

- Every `m2()` run must complete an acceptance-first
  planning pass before the first durable conductor tick may
  dispatch managers, workers, testers, reviewers,
  integration, validation, or delivery work. This applies to
  budgeted and non-budgeted invocations, product and
  non-product work, protocol maintenance, repair, audit, and
  handoff runs.
- Before materializing the acceptance matrix, re-read and
  apply `references/writeAC.protocol.md` as the
  acceptance criteria normalization module. `writeAC()` owns
  scope preservation, atomic criteria, source traceability,
  required evidence, explicit out-of-scope capture, and
  blocking-question handling for acceptance rows.
- `m2()` remains the durable conductor and artifact owner.
  Applying `writeAC` does not make public `writeAC(...)`
  write files; it means `m2()` uses the module contract
  while writing its normal run acceptance artifacts.
- The pass begins with non-mutating discovery. Read the
  invoked plan, project manifest when present, existing
  acceptance matrix rows, packet registry, interface
  contracts, relevant source files, tests, docs, previous
  run artifacts, screenshots, browser state, or external
  reference material needed to understand the requested
  behavior. Do not dispatch implementation to discover the
  acceptance criteria.
- If high-impact intent remains ambiguous after discovery,
  pause before dispatch and ask one focused human question.
  Record the blocker in the run log and acceptance matrix.
- The conductor must materialize a full acceptance matrix at
  `RUN_ACCEPTANCE_MATRIX_PATH` and, when structured output
  is used, `RUN_ACCEPTANCE_MATRIX_JSON_PATH`. When a project
  file network exists, the run matrix must mirror or
  revision-link the project manifest's
  `acceptance_matrix_path`.
- Full matrix means every in-scope expected outcome has an
  acceptance id, source inputs, current-state summary,
  target behavior, affected user or operator journey,
  applicable gates, owning packet ids when known, required
  evidence, status, and blocking questions. For non-UI
  protocol or infrastructure work, the journey may be an
  operator, maintainer, reviewer, or automation journey, and
  the evidence may be lint, schema inspection, command
  output, review proof, or diff inspection.
- The matrix must identify explicit out-of-scope behavior
  and removals when they materially affect implementation. A
  row may be `blocked` only with owner, reason, next action,
  and whether human input is required.
- Packet registry rows, manager plans, worker prompts, TL
  reviews, verification plans, evidence rows, and
  non-stopping delivery events must cite acceptance ids from
  the active matrix. A packet cannot move to
  `ready_for_workers` without at least one cited acceptance
  id unless its only role is acceptance-matrix repair.
- Budget-plan `acceptance_criteria` rows must trace to the
  active acceptance matrix. Non-budgeted runs also use the
  acceptance matrix as the top-line execution target and
  terminal-state basis.
- Acceptance rows are the source of truth for completion. PR
  creation, elapsed time, screenshots alone, queued CI,
  partial implementation, or a clean delivery event never
  count as completion while in-scope matrix rows remain open
  and safe work can still move.
- Any material acceptance change after dispatch requires an
  acceptance-matrix revision event that records old and new
  row ids, reason, owner, invalidated packets, invalidated
  reviews, and stale evidence ids.

Durable conductor contract:

- `m2()` is a durable conductor loop. It is not complete
  after setup, initial planning, initial dispatch, or one
  pass through the phase list.
- The durable conductor loop starts after the plan
  validates, `RUN_EVENTS_PATH` exists,
  `RUN_ACCEPTANCE_MATRIX_PATH` exists or is repaired from
  canonical project/run records, `RUN_BOARD_PATH` and
  `RUN_RESUME_COCKPIT_PATH` exist or are repairable from
  events, and the current `CONDUCTOR_MODE` has been recorded
  in the execution environment artifact.
- A run is terminal only when every required packet is one
  of:
  - `completed` with required evidence;
  - `blocked` with owner, reason, next action, and terminal
    handoff acceptance by Delivery;
  - explicitly removed from scope by a human-approved plan
    update.
- `terminal_completed` requires zero release-blocking
  acceptance rows in the active matrix, zero stale required
  evidence rows, and final Product, Verification, Delivery,
  and Uber TL signoff.
- `terminal_partial_handoff` is the only terminal state for
  a run that ends with accepted blockers.
- `terminal_blocked` means no packet can move without a
  human decision, adapter capability, external service, or
  revised scope.
- A blocked release row cannot be treated as launch-ready
  without explicit human signoff recorded in the decision
  ledger.
- The coordinator must drive repeated control-loop ticks
  until terminal state or an explicit pause condition.
- If `RUN_ITERATION_GOAL` is a positive integer, the
  coordinator must treat that value as the requested
  completed-tick budget for this invocation. Initialize
  `RUN_ITERATIONS_USED=0` for the invocation. After each
  increment-eligible durable conductor tick appends its
  canonical event, increment `RUN_ITERATIONS_USED` by `1`.
  In non-budgeted compatibility runs, reaching
  `RUN_ITERATIONS_USED >= RUN_ITERATION_GOAL` is a clean
  compatibility stop. In budgeted runs, reaching the tick
  budget is evidence for the budget plan but does not
  authorize exit while acceptance criteria remain unmet and
  safe work can still move.
- With a positive `RUN_ITERATION_GOAL`, the coordinator must
  attempt to satisfy the full goal with real team progress.
  It must not hand off after a single useful tick merely
  because the first selected slice is validated. If any safe
  manager, worker, reviewer, tester, integration, or
  validation action remains, continue the next tick toward
  the goal.
- `RUN_ITERATION_GOAL` measures real work, not mere motion.
  A tick counts only when it is increment-eligible under the
  `Real Work Tick Contract`.
- If `RUN_WALL_CLOCK_GOAL_MINUTES` is a positive integer,
  the coordinator must continue productive conductor work
  against that wall-clock budget. Waiting, narration,
  cockpit-only edits, or PR status polling do not satisfy
  product progress while blocking gates remain red, but they
  may run in parallel as health monitoring.
- If both a positive `RUN_ITERATION_GOAL` and a positive
  `RUN_WALL_CLOCK_GOAL_MINUTES` are present, the assistant
  must derive the effective budget from the larger implied
  effort and write a budget plan before product ticks begin.
  Satisfying only the counter or only the wall-clock timer
  is not sufficient for budgeted exit.
- If no `iterations:N` argument is present,
  `RUN_ITERATION_GOAL` is `unbounded`, and the coordinator
  must continue for as many meaningful ticks as safely
  possible until terminal state, explicit pause/stop, or a
  real capability, context, approval, service, or P0 blocker
  prevents another tick.
- The assistant may send a final response only when:
  - the run is terminal;
  - the human explicitly asks to pause or stop;
  - a bounded green tick wrapper has completed exactly one
    durable conductor tick, written current durable state,
    written the exact next wrapper invocation, and recorded
    Final Response Gate status `green_tick_handoff`;
  - in a budgeted invocation, every budget-plan acceptance
    criterion is met;
  - in a non-budgeted invocation, every in-scope acceptance
    matrix row is met, blocked with accepted handoff, or
    superseded;
  - in a non-budgeted compatibility invocation, every
    explicit invocation goal has been satisfied:
    `RUN_ITERATIONS_USED >= RUN_ITERATION_GOAL` when a
    positive tick goal exists and elapsed wall-clock time is
    greater than or equal to `RUN_WALL_CLOCK_GOAL_MINUTES`
    when a positive duration goal exists;
  - no safe packet can move and the blocker has owner,
    reason, and next action;
  - context, tool, approval, capability, or service limits
    prevent another meaningful tick;
  - in a budgeted invocation, elapsed wall-clock time has
    exceeded `RUN_BUDGET_OVERRUN_EXIT_MINUTES` and the
    overrun handoff records unmet acceptance criteria;
  - a P0 blocker requires human decision.
- The assistant must not send a final response merely
  because a PR was opened, pushed, marked ready for review,
  or left with pending checks. Record that non-stopping
  delivery event, monitor checks as health data, and
  continue the next tick until budget acceptance, all
  non-budgeted explicit invocation goals, or a real stop
  condition is reached.
- If the assistant sends a non-terminal final response
  before an explicit tick or duration goal is reached, it
  must record the deficit as `RUN_ITERATION_GOAL_SHORTFALL`
  and/or `RUN_WALL_CLOCK_GOAL_SHORTFALL_MINUTES` and explain
  the stop reason as a real blocker or limit, not as normal
  completion.
- If the run is not terminal, the final response must say
  `m2 run not terminal`, include `RUN_ID`, `RUN_LOG_PATH`,
  `RUN_BOARD_PATH`, active packets, blocked packets, active
  agents or worktrees, last completed tick,
  `RUN_ITERATIONS_USED`, `RUN_ITERATION_GOAL`,
  `RUN_WALL_CLOCK_ELAPSED_MINUTES`,
  `RUN_WALL_CLOCK_GOAL_MINUTES`,
  `RUN_ITERATION_GOAL_SHORTFALL` when positive,
  `RUN_WALL_CLOCK_GOAL_SHORTFALL_MINUTES` when positive,
  `RUN_ITERATION_STOP_REASON`, and the exact resume
  invocation. Link `RUN_RESUME_COCKPIT_PATH`.
- A normal status update is not a final response. After a
  status update, continue the next tick unless the human
  asks to pause or stop.

Real Work Tick Contract:

- A tick is increment-eligible only if it creates durable
  artifact-level forward motion in at least one of these
  forms:
  - a declared blocking gate moves from `red` to `yellow`,
    `red` to `green`, or `yellow` to `green`;
  - new or revised code diff for a concrete packet;
  - integrated diff or conflict-resolution artifact;
  - targeted validation result that changes packet state;
  - browser evidence against the current implementation
    worktree that changes packet state or confirms a shipped
    slice;
  - blocker removal that unlocks dispatch, integration, or
    validation;
  - review finding or approval that changes dispatchability
    or integration readiness;
  - non-stopping delivery event backed by new integrated
    code or new evidence.
- Before incrementing `RUN_ITERATIONS_USED`, the tick must
  satisfy the Tick Eligibility Checklist. Its canonical
  event must record gate ids, `tick_value_type`, changed
  paths or evidence paths, validation command and status
  when validation ran, `localhost_url` when browser-facing,
  `lane_role` for product-gated runs, `increment_reason`,
  and the next concrete action.
- A tick that cannot fill the checklist must set
  `increment_eligible=false` and classify as
  `non_increment_eligible_support`, even if it produced
  useful narration, PR polling, or cockpit maintenance.
- When `ACTIVE_BLOCKING_GATE_IDS` is non-empty, a productive
  tick must classify itself as exactly one of:
  - `gate_advance`;
  - `gate_supporting_code`;
  - `gate_supporting_validation`;
  - `non_increment_eligible_support`.
- When `ACTIVE_BLOCKING_GATE_IDS` is non-empty, docs,
  protocol, plan, cockpit, or status-only work is not
  increment-eligible unless the tick also lands code, tests,
  evidence, or blocker removal that directly unblocks one of
  those active blocking gates.
- When `ACTIVE_BLOCKING_GATE_IDS` is non-empty, pull request
  creation, PR waiting, check polling, status narration, or
  queue watching must classify as
  `non_increment_eligible_support` unless the same tick also
  advances a blocking gate or records fresh gate-attached
  code or validation evidence.
- A `breadth_lane` tick attached to declared
  `next_capability`, `reliability`, or `delivery_meta` gates
  may be increment-eligible while active blocking gates
  exist only when the Requested M1 Lane Count Rule permits
  the breadth lane and the tick lands real code, tests,
  browser evidence, integration, or blocker removal. It must
  not count when it is only roadmap discussion, protocol
  refinement, PR waiting, or cockpit grooming.
- A tick is not increment-eligible when it consists only of
  summaries, queue watching, waiting, repeated scans,
  protocol or plan edits, cockpit grooming, PR hygiene
  without new code or evidence, or planning refinement
  without new dispatch, integration, validation, or blocker
  resolution.
- Support-only ticks may still append canonical events, but
  they must set `increment_eligible=false` and must not
  increment `RUN_ITERATIONS_USED`.
- After safe edit scopes exist, two consecutive support-only
  ticks are a protocol violation. The next tick must
  dispatch, integrate, validate, or record a formal blocker
  that explains why no real work can move.
- If two consecutive productive ticks leave every
  `ACTIVE_BLOCKING_GATE_ID` unchanged, the conductor must
  rescope manager ownership, packetization, or verification
  strategy before continuing.
- Momentum Watchdog: if two consecutive ticks produce no
  gate movement, code diff, integrated change, fresh
  evidence, or blocker removal, the next tick must choose a
  smaller gate slice, change delegation, rescope packet
  ownership, or record a formal blocker. More status,
  protocol, or PR-watching work cannot count until momentum
  is restored.

Transactional Run State Contract:

- `RUN_EVENTS_PATH` is the canonical run state. Markdown
  cockpit artifacts are derived human-readable views.
- Every event is appended as one JSON object line. Existing
  event lines are never edited.
- Every tick appends an event with:
  - `tick_id`;
  - `parent_tick_id`;
  - UTC timestamp;
  - `execution_mode`;
  - `tick_classification`;
  - `tick_value_type`;
  - `increment_eligible`;
  - lifecycle state before and after;
  - `blocking_gate_ids`;
  - gate updates with `gate_id`, `gate_status_before`, and
    `gate_status_after`;
  - `evidence_paths`;
  - `localhost_url`;
  - `trace_path`;
  - packet changes;
  - adapter operations;
  - worktree snapshots;
  - git branch and SHA snapshots;
  - artifact paths and hashes;
  - `real_work_result`;
  - `support_work_result`;
  - validation result;
  - review result;
  - blocker or terminal result.
- A tick updates required derived artifacts only after the
  canonical event is appended.
- Required derived artifacts are:
  - `RUN_BOARD_PATH`;
  - `RUN_RESUME_COCKPIT_PATH`;
  - the current lifecycle and handoff sections of
    `RUN_LOG_PATH`.
- Optional derived artifacts include `RUN_TICK_PATH` and the
  remaining cockpit markdown files under `RUN_ARTIFACT_DIR`.
  They should be materialized when useful, when the plan
  explicitly asks for them, or when a human asks for richer
  operator visibility, but they must not block useful work
  if missing or stale.
- For product-gated runs, `RUN_GATE_STATUS_PATH` and
  `RUN_GATE_STATUS_JSON_PATH` are preferred derived views
  rebuilt from `RUN_EVENTS_PATH`. Missing or stale gate
  dashboards must never block useful work when the canonical
  event log is intact.
- Derived Markdown artifacts must record the latest
  `tick_id` and source event hash when they exist.
- On resume, reconcile `RUN_EVENTS_PATH` against
  `RUN_BOARD_PATH`, `RUN_RESUME_COCKPIT_PATH`, and any
  materialized cockpit files. If Markdown is stale or
  missing, repair it from events before dispatch.
- If `RUN_EVENTS_PATH` is missing during resume, block
  resume unless a human explicitly accepts recovery from the
  older Markdown artifacts.

Interface Lock Gate:

- Shared interfaces require stable contract records before
  worker dispatch.
- Each contract record must have `contract_id`, owner,
  consuming packets, symbols or fields, compatibility
  requirements, defaults, error behavior, tests, and
  signoffs.
- Packets that touch shared interfaces cannot move from
  `tl_review` to `ready_for_workers` until every referenced
  contract is accepted by owning and consuming managers.
- Contract changes after worker dispatch invalidate affected
  reviews, evidence rows, and worker prompts.

Behavior Gate Contract:

- Product runs may declare blocking behavior gates in the
  plan, acceptance matrix, interface contracts, or
  project-specific gate pack.
- The canonical event log is the source of truth for gate
  state. Derived dashboards or markdown mirrors are
  rebuildable views, not gate truth.
- Every productive tick in a product-gated run must record:
  - `blocking_gate_ids`;
  - `tick_value_type`;
  - zero or more gate updates with `gate_id`,
    `gate_status_before`, and `gate_status_after`;
  - fresh `evidence_paths` when the tick produced tests,
    browser proof, screenshots, summaries, traces, or other
    artifacts used to assess those gates;
  - `localhost_url` when the tick exercised a localhost
    browser surface;
  - `trace_path` when the tick produced a browser trace.
- A declared blocking gate stays blocking until its latest
  canonical state is `green`. Missing evidence keeps the
  gate red.
- The conductor must prefer packets that can advance red
  gates before packets that only polish already-green areas.
- Gate-attached code without fresh evidence may count as
  `gate_supporting_code`, but it does not change gate color
  until validation or browser proof records a gate update.
- Gate-attached browser or targeted validation evidence may
  count as `gate_supporting_validation` even when the gate
  stays red, as long as the evidence materially informs the
  next safe edit or rescoping decision.
- A non-stopping delivery event, PR open, PR merge, or
  queued check is never by itself a gate advance.

Gate Portfolio Contract:

- Product-gated plans must maintain a gate portfolio that
  separates current blocking gates, next capability gates,
  reliability gates, and delivery/meta gates.
- Current blocking gates define the active release or run
  truth. They must list gate id, owner manager, source,
  evidence rule, current status, estimate range when known,
  and next packets.
- Next capability gates describe product breadth that is
  real but not yet blocking for the current run. They must
  not stop delivery, consume blocking-gate priority, or be
  reported as release blockers until promoted by plan,
  acceptance-matrix, interface-contract, or run-event
  decision.
- Reliability gates cover deploy, performance,
  observability, startup, cache, data-loss, and scale
  behavior. They may become current blockers when failures
  threaten launch, data integrity, or the active product
  proof.
- Delivery/meta gates cover conductor health, PR flow,
  resume durability, dashboards, screenshots, review
  hygiene, and tick integrity. They are product-enabling
  gates, but while UX or browser behavior gates are red,
  they are increment-eligible only when they directly
  unblock product progress or produce required evidence.
- Gate source must be explicit. Project-plan-backed gates,
  acceptance-matrix gates, interface-contract gates,
  human-requested gates, run-event gates, and inferred
  roadmap gates are distinct sources. Inferred roadmap gates
  must be labeled as such and remain non-blocking until a
  later explicit promotion records them as current blockers.
- If a chat-derived or inferred product roadmap becomes
  useful enough to guide work, the conductor must persist it
  into the plan or project root before relying on it for
  packet priority, estimates, or resume state.

BFS/DFS Portfolio Balance Contract:

- Product-gated runs must balance depth-first correctness
  with breadth-first product coverage. Deep work on the
  highest-risk gate is necessary, but it must not become a
  single-gate tunnel when other common user journeys can
  safely move.
- Active product lanes must be classified as one of:
  `depth_lane`, `breadth_lane`, `stabilization_lane`, or
  `evidence_lane`.
- A `depth_lane` owns hard correctness, polish, regression
  repair, and current-blocker closure for the highest-risk
  active gate family.
- A `breadth_lane` owns a different customer/user journey or
  gate family so the product surface widens while deep work
  continues. Breadth lanes must still land real code, tests,
  browser evidence, integration, or blocker removal; they
  are not permission for status-only or docs-only activity
  to count as progress.
- A `stabilization_lane` keeps recently green or yellow
  blocking gates from regressing while new breadth opens.
- An `evidence_lane` proves an active depth, stabilization,
  or breadth lane with targeted tests, localhost/browser
  proof, screenshots, traces, or review bundles tied to the
  same gate ids.
- Multiple requested lanes means multiple distinct product
  domains, common user journeys, gate families, or evidence
  scopes. Multiple workers on the same narrow packet may be
  valid fanout, but it does not satisfy the requested M1
  lane count by itself.

Requested M1 Lane Count Rule:

- `RUN_NUM_M1S` controls the requested number of parallel
  active M1 manager-of-IC lanes for the invocation. The
  default is `1`.
- When `RUN_NUM_M1S` is `1`, the conductor may keep one
  depth or stabilization lane active and go deep, while
  still using lower-level SWE, test, or evidence workers
  inside that lane when safe.
- When `RUN_NUM_M1S` is greater than `1`, the conductor must
  keep up to `RUN_NUM_M1S` unique M1 lanes active, or record
  the concrete write-scope, dependency, validation,
  capability, or capacity blocker that prevents reaching the
  requested lane count.
- When two or more safe product lanes exist and
  `RUN_NUM_M1S` is greater than `1`, at least one lane must
  be a depth or stabilization lane and at least one lane
  must be a breadth lane.
- While any current blocking gate is red, one lane must stay
  focused on the red blocker. A bounded breadth lane may run
  in parallel only when `RUN_NUM_M1S` is greater than `1`
  and its write scope, validation needs, and attention cost
  do not compromise blocker closure.
- Once current blocking gates are green or yellow in fresh
  evidence, the conductor must keep one stabilization lane
  on those gates. If `RUN_NUM_M1S` is greater than `1`, it
  must also open at least one roadmap or capability breadth
  lane when safe.
- Intended long runs of four hours or longer should prefer
  explicit `numM1s` values rather than relying on the
  default. Values of `2` to `4` are the normal range for
  broad product progress, subject to file leases, review
  safety, and runnable evidence. Do not create unsafe file
  conflicts or unreviewable patch piles merely to satisfy
  lane count.
- Breadth-lane ticks may be increment-eligible when they
  land code, tests, browser evidence, integration, or
  blocker removal attached to declared `next_capability`,
  `reliability`, or `delivery_meta` gates.
- Docs-only, narration-only, PR-waiting, or cockpit-only
  breadth work remains `non_increment_eligible_support`
  unless the same tick also produces real gate-attached
  code, validation, evidence, integration, or blocker
  removal.
- If a current blocking gate regresses to red, the next
  depth lane must address that regression before breadth
  expands further. Existing breadth work may continue only
  when it is already safe, isolated, and does not delay the
  regression repair.

Gate Execution Process Contract:

- Large product gates must be decomposed into small SWE
  packets that are normally finishable in 30 to 90 minutes.
  Each packet names its gate ids, owner manager, allowed
  write scope, expected evidence, validation commands, and
  next packet on success.
- Every gate family must have an M1 manager owner. The
  conductor owns cross-manager priority, integration,
  review, and blocker arbitration; M1 managers own
  lower-level design, packetization, and SWE dispatch inside
  their gate family.
- Whenever runnable, every code lane must have a parallel
  evidence lane. Evidence lanes may add or run browser
  proof, screenshots, traces, targeted tests, diff
  summaries, review bundles, or resume artifacts tied to the
  same gate.
- A coherent PR slice may be opened or updated at any time,
  but its proof must name gate ids, commit, branch, PR URL,
  validation commands, canonical demo URL when
  browser-facing, any localhost proof URL, evidence paths,
  and next packet.
- If two productive ticks fail to move any active blocking
  gate or produce new gate-attached code, validation,
  evidence, integration, or blocker removal, the conductor
  must rescope the gate into smaller packets, change the M1
  ownership, or record the concrete blocker.
- The intended operating shape is a gate factory: choose a
  red or highest-risk gate, cut the smallest observable
  packet, implement, prove, push, refresh resume state, and
  immediately feed both the next depth packet and the next
  safe breadth packet when available.

Gate Estimate Contract:

- Gate portfolios may include rough planning estimates:
  `hours_low`, `hours_high`, `ticks_low`, and `ticks_high`.
- Estimates are capacity-planning ranges, not promises,
  deadlines, terminal criteria, or permission to stop when a
  gate is still red.
- Estimate records must identify their source, such as prior
  measured pace, human planning request, project manager
  estimate, or inferred roadmap synthesis.
- Substantial evidence changes should refresh estimates.
  Examples include a gate moving to yellow or green, a major
  scope change, a repeated validation failure, a new
  dependency, a large review finding, or measured run pace
  diverging materially from the previous estimate.
- Unknown estimates should be `null` rather than invented.
  If the conductor provides an inferred estimate, label it
  as inferred and keep it non-authoritative until reviewed
  by the owning manager.

Budget Endstate Planning Contract:

- Every invocation with `iterations:N`, `duration:D`, or
  both must produce a budget-to-endstate plan before the
  first product tick. This plan is required even when the
  run is resuming from an existing runnable resume prompt.
- Use `1000 ticks = 1 hour` as the canonical planning ratio.
  Therefore `250 ticks = 15 minutes`.
- The canonical ratio is single-lane budget math unless the
  human or plan capsule explicitly defines a multi-lane
  aggregate interpretation. In the aggregate case, record
  `aggregate_m1_ticks` and `per_lane_ticks` separately from
  wall-clock duration. Do not stretch wall-clock minutes to
  match aggregate ticks across lanes.
- Compute the effective budget with these values:
  - `budget_minutes` from `duration:D` when present;
  - `budget_ticks` from `iterations:N` when present;
  - `aggregate_m1_ticks` from the explicit aggregate M1
    statement when present, otherwise `null`;
  - `per_lane_ticks = aggregate_m1_ticks / numM1s` when
    aggregate M1 ticks are present and evenly divisible,
    otherwise an explicit per-lane distribution in
    `lane_plan`;
  - `effective_budget_ticks = max(explicit_ticks, duration_minutes * 1000 / 60)`
    when both are present, or the single supplied value
    converted to ticks;
  - `effective_budget_minutes = max(explicit_minutes, explicit_ticks * 60 / 1000)`
    when both are present, or the single supplied value
    converted to minutes;
  - `budget_slice_count = ceil(max(effective_budget_ticks / 250, effective_budget_minutes / 15))`.
- In aggregate M1 mode, `effective_budget_minutes`,
  `time_overrun_exit_minutes`, and budget exit decisions
  remain based on the explicit wall-clock `duration:D` when
  present. For a 4-hour aggregate run, record
  `budget_minutes=240`, `effective_budget_minutes=240`, and
  `time_overrun_exit_minutes=264`, even when
  `aggregate_m1_ticks=16000`.
- The startup budget plan must name the intended endstate of
  the system after the supplied budget, not merely the next
  PR. It must include:
  - target endstate narrative;
  - gate movement targets;
  - acceptance criteria derived from active acceptance
    matrix rows shaped by `writeAC` and citing active
    acceptance matrix ids;
  - user journeys;
  - M1 lane allocation;
  - 15-minute or 250-tick milestone slices;
  - screenshot, browser, manual click-through,
    mouse-through, keyboard, trace, or test evidence planned
    for each browser-facing slice.
- Each milestone slice must identify its minute range, tick
  range, owner M1, lane role, gate ids, planned deliverable,
  validation or evidence, and expected user-visible delta.
- Large budgets must still be represented at 15-minute or
  250-tick resolution. The markdown view may group slices by
  hour for readability, but every slice id and tick/minute
  range must remain explicit in the budget plan record.
- The budget plan is allowed to change when evidence,
  blockers, or human scope changes prove the old plan wrong,
  but the change must be recorded as a budget-plan revision
  event with old and new acceptance criteria.
- Budget-plan acceptance criteria must not be drafted as
  fresh ad hoc prose. They must trace to active acceptance
  matrix rows normalized through `writeAC`, and any new
  budget acceptance need must first become an acceptance
  matrix revision.

Budget Lease Contract:

- Any invocation with `iterations:N`, `duration:D`, or both
  creates a budget lease. The lease is the minimum execution
  commitment for the primary conductor thread, not a loose
  suggestion and not merely a prompt-shaping hint.
- `duration:D` is a minimum wall-clock lease. The conductor
  must keep working until that wall-clock minimum is met,
  unless the human stops it, terminal state is reached, an
  overrun handoff is required, or all lanes are truly
  blocked.
- `iterations:N` is a minimum productive tick target. Ticks
  are counted only after increment-eligible product,
  evidence, integration, review, or blocker-removal work
  appends canonical state.
- For `numM1s:M` aggregate mode, track wall-clock minutes,
  per-lane ticks, and aggregate M1 ticks as separate values.
  Aggregate M1 ticks measure team throughput; they do not
  silently extend or shorten the wall-clock lease.
- PR creation, PR updates, pushes, screenshots, green
  localhost validation, deploy proof, and queued CI are
  non-stopping `delivery_event` records inside the lease.
  They are never completion by themselves.
- After every non-stopping delivery event, the conductor
  must choose and record
  `RUN_POST_DELIVERY_EVENT_NEXT_PACKET`, reassign or
  redirect M1s as needed, and continue the loop while safe
  work remains and the lease is not eligible to stop.
- A high-quality slice may satisfy one acceptance criterion,
  but it cannot satisfy the lease unless the full
  budget-plan acceptance set is met or a valid stop reason
  exists.
- A final response or non-terminal handoff before the lease
  is satisfied is allowed only when the
  `Final Response Gate` returns `human_paused`, `terminal`,
  `true_blocker`, or `overrun_handoff`.

Budget Exit Contract:

- A primary budgeted `m2()` invocation must not exit merely
  because a PR was opened, a branch was pushed, CI is
  queued, screenshots were captured, browser proof passed,
  or a clean non-stopping delivery event exists.
- Once a budget plan exists, the primary invocation may exit
  only when one of these conditions is true:
  - every budget-plan acceptance criterion is met and the
    wall-clock and tick lease minimums are satisfied;
  - terminal state is reached;
  - the human explicitly pauses or stops the invocation;
  - a true blocker prevents every safe next packet from
    moving;
  - elapsed wall-clock time exceeds
    `effective_budget_minutes * 1.10`.
- If acceptance criteria are met before the effective tick
  or wall-clock lease is consumed, record early acceptance
  evidence and continue with the next planned or adjacent
  safe packet. Clean exit requires both acceptance and lease
  satisfaction.
- If elapsed time exceeds the 110% overrun threshold while
  acceptance criteria remain unmet, the invocation must exit
  with a non-terminal overrun handoff, not a success claim.
  That handoff must include unmet acceptance criteria, gate
  shortfalls, tick shortfall, elapsed minutes, active lanes,
  current evidence paths, and exact resume invocation.
- If the invocation exits for a true blocker before
  acceptance is met, the handoff must identify why no safe
  implementation, verification, evidence, review,
  integration, or research packet can move.
- `duration_goal_reached`, `iteration_goal_reached`, and
  `iteration_and_duration_goals_reached` are not valid stop
  reasons for a budgeted invocation. Counter or time
  satisfaction must flow through `Final Response Gate`, and
  `duration_goal_reached` alone is never sufficient when
  acceptance criteria remain unmet.

Final Response Gate:

- Before any final response, pause handoff, terminal
  handoff, overrun handoff, or non-budgeted compatibility
  stop, the conductor must compute and write: elapsed
  minutes, completed increment-eligible ticks, aggregate M1
  ticks completed when applicable, active lanes,
  non-stopping delivery event count, PR/check/deploy state,
  unmet acceptance criteria, and the next safe packet
  candidates.
- The gate returns exactly one status: `continue_required`,
  `budget_acceptance_met`, `human_paused`, `true_blocker`,
  `terminal`, or `overrun_handoff`.
- The gate may return `budget_acceptance_met` only when the
  budget-plan acceptance criteria are met, the minimum
  wall-clock/tick lease is satisfied, and there is no safe
  next deliverable available under the
  `Post-Delivery Continuation Contract`.
- A final response, pause handoff, or non-terminal handoff
  is forbidden while the gate status is `continue_required`.
  The conductor must select or refresh the next packet and
  continue instead.
- If the run is budgeted, either elapsed wall-clock time is
  below the requested duration or completed ticks are below
  the minimum tick target, and any safe implementation,
  verification, evidence, review, integration, research, or
  blocker-removal packet can move, the gate must return
  `continue_required`.
- If the run is budgeted and a non-stopping delivery event
  just succeeded while the lease is not eligible to stop,
  the gate must return `continue_required` after recording
  `RUN_POST_DELIVERY_EVENT_NEXT_PACKET`.
- If the run is budgeted and a non-stopping delivery event
  just succeeded while any safe next deliverable exists, the
  gate must return `continue_required` even when the latest
  event produced green gates, passing CI, a pushed commit, a
  PR proof comment, a ready PR, or a refreshed resume
  prompt/capsule.
- If the requested duration has elapsed but acceptance
  remains unmet, the gate must still return
  `continue_required` until either the acceptance set is
  met, a valid blocker/terminal/human stop appears, or
  elapsed time exceeds the overrun threshold.
- If the conductor attempts to final-response while the gate
  status is `continue_required`, set
  `RUN_EARLY_STOP_VIOLATION=true`, append an event to
  `RUN_EVENTS_PATH`, select the next packet, and continue.
- Set `RUN_EARLY_STOP_VIOLATION=true` with an appropriate
  reason such as `stopped_after_validation`,
  `stopped_after_push`, `stopped_after_ci_queue`,
  `stopped_after_delivery_event`, or
  `stopped_after_clean_slice` whenever the attempted final
  response follows green validation, a push, PR comment,
  passing/queued/skipped CI, ready PR state, or resume
  prompt/capsule refresh but the gate still requires
  continuation.
- Every final output or non-terminal handoff for a budgeted
  invocation must include the stop reason:
  `budget_acceptance_met`, `human_paused`, `true_blocker`,
  `terminal`, or `overrun_handoff`.

Long-Run Preparation Contract:

- Before any intended run of four hours or longer, or any
  saved prompt with a minimum wall-clock goal of at least
  240 minutes, or any invocation with `duration:4h` or a
  larger normalized duration, the conductor must refresh
  runnable resume state before product ticks begin.
- Long-run resume state must include worktree, branch,
  active PRs, latest known commit, canonical demo URL, any
  localhost proof URL, validation artifact paths, local-only
  excludes, active blocking gates, next capability gates,
  next two to five packets, minimum wall-clock minutes,
  minimum increment-eligible ticks, and stop policy.
- The run must verify that local-only artifacts remain
  untracked, the active worktree is usable, the PR state is
  known or explicitly marked unknown, and the localhost demo
  is healthy or restartable.
- Long-run tick targets may be derived from a plan-declared
  baseline ratio. The default baseline ratio is 1000 ticks
  per hour. When no explicit ratio exists in an old plan,
  preserve the latest saved prompt policy unless the human
  supplies an override.
- Long-run prompts that declare aggregate M1 tick budgeting
  must include the lane count, wall-clock duration,
  `aggregate_m1_ticks`, and `per_lane_ticks`. The saved
  wall-clock duration remains the overrun basis; aggregate
  M1 ticks are throughput accounting, not a hidden extension
  of the wall-clock goal.
- A long-run non-stopping delivery event must not rewrite
  the baseline ratio accidentally. Explicit `iterations:N`
  overrides the current invocation only, and explicit
  `duration:D` overrides the current invocation only, unless
  the regenerated resume prompt intentionally records a new
  durable policy.

Review Lifecycle:

- Every review has `review_id`, reviewer role, target
  artifact path, target artifact hash, target diff hash when
  applicable, required scope, verdict, findings, finding
  state, and invalidation conditions.
- Review findings move through `open`, `addressed`,
  `accepted_risk`, or `superseded`.
- P0 and P1 findings block worker dispatch and integration.
- Reviews must be re-run when target diffs, dependent
  contracts, file leases, acceptance criteria, or validation
  evidence change.
- The review queue must show pending, blocked, accepted, and
  invalidated reviews separately.

Evidence Freshness:

- Evidence rows must include packet id, acceptance row id,
  command or browser action, worktree path, branch, commit
  SHA, artifact path, artifact hash, fixture id, fixture
  version, packet version, timestamp, and invalidation
  dependencies.
- Delivery rejects evidence that predates relevant
  integration commits, contract changes, fixture changes, or
  acceptance row changes.
- Evidence attached to a worker branch is not final release
  evidence until it is reproduced or accepted against the
  integration worktree.

Security And Privacy Gate:

- A security and privacy review is required for packets that
  touch network routes, storage, auth, secrets, subprocess
  execution, user data, file paths, dependency changes,
  browser data handling, external services, or artifact
  retention.
- Security review must record threat surface, sensitive data
  exposure, input validation, path safety, subprocess
  safety, dependency risk, logging redaction, and rollback
  plan.
- A packet cannot integrate with unresolved P0 or P1
  security findings.

Each tick must produce at least one of these outcomes:

- packet state transition;
- agent dispatch, resume, or close;
- accepted evidence artifact;
- review finding with owner;
- integration attempt with result;
- non-stopping delivery event with commit, push, PR, or

- validation command with result;

Resume rules:

- Bare `m2(plan_path)` is allowed to resume durable work
  without an explicit `resume:` argument. It must first
  evaluate `PLAN_RESUME_PROMPT_POINTER_PATH`; when that
  pointer names a compatible non-terminal run or plan-level
  resume capsule, load the runnable prompt record and treat
  its `prompt_text` as the effective continuation prompt.
  This is the normal way simple `m2()` invocations inherit
  the full saved resume prompt between calls.
- `m2(plan_path, resume:RUN_ID)` may be invoked from any
  compatible repo worktree that can read the plan and the
  run artifacts. Prefer continuing in the recorded
  `CONDUCTOR_MODE` and conductor surface when they still
  exist.
- `iterations:N` may be used with either start or resume
  invocations. It must be preserved across any relocation or
  same-thread recovery and must be treated as the current
  invocation's production goal. When a saved runnable prompt
  also contains a tick goal, the explicit `iterations:N`
  wins for the current invocation only. It must not be
  written as a persistent run setting unless a subsequent
  resume-prompt regeneration intentionally records it.
- `duration:D` may be used with either start or resume
  invocations. It must be preserved across any relocation or
  same-thread recovery and must be treated as the current
  invocation's minimum wall-clock goal. When a saved
  runnable prompt also contains a wall-clock goal, the
  explicit `duration:D` wins for the current invocation
  only. It must not be written as a persistent run setting
  unless a subsequent resume-prompt regeneration
  intentionally records it.
- When both `iterations:N` and `duration:D` are supplied on
  resume, the resumed run continues until both invocation
  goals are satisfied, unless terminal, paused, stopped, or
  truly blocked.
- On resume, if the run recorded `same_thread`, continue in
  the compatible dedicated implementation or conductor
  worktree when available. If the run recorded
  `isolated_control`, locate the recorded control worktree
  or recreate an equivalent isolated surface from
  `RUN_EVENTS_PATH` and then continue there.
- Resume must load `RUN_EVENTS_PATH`, `RUN_LOG_PATH`,
  `RUN_BOARD_PATH`, `RUN_RESUME_COCKPIT_PATH`, and
  `RUN_RESUME_PROMPT_PATH` when a non-terminal run already
  has one, repairing missing or stale derived Markdown and
  runnable prompt text from events before dispatch.
- On resume, derive the expected `RUN_LOG_PATH` from
  `RUN_ID` and `PLAN_SLUG`. If that exact path is missing,
  search `${ACTIVE_REPO_ROOT}/.agents/logs/` and
  `${RUNS_ROOT}` for `<RUN_ID>-m2-*.gpt.md`. Exactly one
  match may be used, and that run log must match
  `PLAN_STORE_IDENTITY` and `PLAN_STORE_RELATIVE_PATH`.
  Multiple matches or a plan mismatch block resume until the
  human resolves ambiguity.
- Resume must reconcile live git status, active worktrees,
  active agents when known, validation artifacts, and any
  user edits made since the last tick.
- Resume must refresh the runnable resume prompt after that
  reconciliation when worktree, branch, PR, localhost URL,
  validation artifacts, stop policy, or next-target state
  has changed.
- Resume must not restart completed packets unless their
  evidence is missing or invalidated by a later integration.
- Resume must not discard worker diffs, review findings, or
  blockers from prior ticks.
- Resume must not require optional cockpit markdown,
  optional devcontainer proof markdown, or an old fixed-path
  control worktree when the canonical event log is present
  and a compatible conductor surface can be recovered.
- If no run artifact exists for `RUN_ID`, stop and report
  that the run cannot be resumed.

Execution phases:

1. Phase 0 `Environment and execution mode`.
   - Read `AGENTS.md`.
   - Capture `INVOCATION_CWD`, `INVOCATION_GIT_ROOT`,
     `INVOCATION_BRANCH`, and `INVOCATION_HEAD`.
   - Derive `HOST_PLAN_STORE_DIR`, `PLAN_PATH`,
     `PLAN_SOURCE_PATH`, `PLAN_STORE_IDENTITY`,
     `PLAN_STORE_RELATIVE_PATH`, `PLAN_IDENTITY_SHA256`,
     `PLAN_SOURCE_COMMIT`, `PLAN_SOURCE_BLOB_ID`,
     `RUNS_ROOT`, `RUN_ROOT`, and `CONDUCTOR_MODE`.
   - If the current shell is not a valid repo and tool
     context for the next planned command, enter a valid
     repo or devcontainer context. Do not relocate only for
     protocol ceremony.
   - On `start` with `CONDUCTOR_MODE=same_thread`, keep the
     current dedicated worktree as the conductor surface and
     default integration surface.
   - On `start` with `CONDUCTOR_MODE=isolated_control`,
     create or locate `CONTROL_WORKTREE` on
     `CONTROL_BRANCH`, plus `INTEGRATION_WORKTREE` when a
     separate clean integration surface is warranted.
   - On `resume`, prefer the previously recorded conductor
     surface. If it no longer exists, recover the safest
     compatible surface from `RUN_EVENTS_PATH` and record
     the mode or path change explicitly.
   - Preserve `iterations:N` and `duration:D` across any
     relocation or recovery. Setup work does not consume an
     iteration.
   - Ensure `PLAN_SOURCE_PATH` exists in its plan store
     (canonical `~/<plan-store>`, or the backing
     `<owner>/<project-store>` worktree for a deprecated
     project-local plan) and
     remains readable from the current conductor surface. If
     `PROJECT_ROOT` is present and the conductor surface
     differs from `PROJECT_SOURCE_ROOT`, seed only the
     declared project file network needed for execution;
     never seed the plan itself.
   - Create the minimum durable artifacts before the first
     durable conductor tick:
     - `RUN_LOG_PATH`;
     - `RUN_ARTIFACT_DIR`;
     - `RUN_EVENTS_PATH`;
     - `RUN_BOARD_PATH`;
     - `RUN_RESUME_COCKPIT_PATH`.
   - Create or refresh `RUN_ISOLATION_PATH` whenever
     `CONDUCTOR_MODE=isolated_control`, when a same-thread
     run changes surfaces, or when recovery would benefit.
   - Create optional proof markdown such as
     `RUN_CONTROL_WORKTREE_PATH` or
     `RUN_DEVCONTAINER_PROOF_PATH` when the plan requires
     it, when the environment is ambiguous, or when a human
     asks for it. Do not let missing optional proof markdown
     delay the first useful tick.
   - If the active checkout is shared or protected, keep it
     read-only and move edit-capable work to a dedicated
     implementation, integration, or worker worktree.

2. Phase 1 `Load and validate the plan`.
   - Read `PLAN_PATH`.
   - Apply the plan-file validation rules above.
   - If `PROJECT_ROOT` is present, read `PROJECT_MANIFEST`,
     plus the project manager files, packet registry,
     acceptance matrix, file leases, subprojects, worker
     prompts, and any declared gate pack or interface
     contract records needed for the next dispatch. Do not
     block on loading future-only files that the current
     tick does not need.
   - Read every referenced manager charter and live plan
     needed for the next safe dispatch.
   - Read the `l8()` protocol before TL or Uber TL review.
   - Create `RUN_LOG_PATH` with run metadata, conductor
     branch, conductor head, conductor dirty status, active
     worktree status, plan path, execution mode,
     environment-record links when present, and lifecycle
     status `planning`.
   - Record selected manager, worker, tester, TL, and Uber
     TL models in the run log. If model selection is
     unavailable, use the current model and record that
     fallback.
   - On `start`, create the minimum required artifacts from
     Phase 0. Create optional cockpit files lazily when the
     tick needs them or the plan explicitly requires them.
   - On `resume`, load existing run artifacts, reconcile
     them with the plan, repair stale derived markdown from
     `RUN_EVENTS_PATH`, and append a resume event before new
     dispatch.

3. Phase 2 `Open the MoM control board`.
   - Build an in-memory board from the plan and any existing
     canonical events:
     - project manifest when present;
     - managers;
     - reports;
     - work packets;
     - dependencies;
     - blocking behavior gates;
     - write scopes;
     - denied paths;
     - file leases;
     - review gates;
     - validation gates;
     - design iteration loops;
   - Mark every packet `pending` unless the plan includes
     evidence for another state.
   - Assign one manager as directly responsible for every
     packet. Do not leave shared ownership ambiguous.
   - Reject the board if any packet lacks a canonical packet
     row with owner, allowed paths, denied paths,
     dependencies, acceptance evidence, tests, integration
     owner, rollback or fallback, status artifact, and stop
     conditions.
   - Reject the board if two edit-capable packets can touch
     the same file without a lease order or stacked-patch
     rule.
   - Reject the board if a product-gated packet lacks named
     gate ids, expected evidence, or a rule that explains
     how the packet can change at least one blocking gate.
   - Persist the board to `RUN_BOARD_PATH` after every
     status transition. `RUN_EVENTS_PATH` is the canonical
     source of truth; in-memory board state is never the
     only source of truth.
   - Mirror packet status, dependency waits, stale packets,
     and next actions into optional cockpit markdown when it
     is materialized or the plan explicitly requires it.

4. Phase 3 `Manager planning loop`.
   - For each manager that owns a currently movable packet,
     unresolved blocker, or cross-team contract decision:
     - dispatch a manager-planning agent with the relevant
       charter, plan sections, write scope, and required
       output schema;
     - that agent runs the `m1()` protocol
       (`references/m1.protocol.md`) for its
       lane, which owns packet shaping, exact file
       ownership, gate ids, interface-contract records,
       fan-out, per-worker supervision rows, and the exit
       state.
   - Keep manager planning practically parallel. When two or
     more independent domains can move and `RUN_NUM_M1S` is
     greater than `1`, keep up to `RUN_NUM_M1S` active M1
     manager lanes unless a recorded capacity or lease
     constraint prevents it.
   - If a manager has no active worker, no pending
     integration decision, and no concrete blocker while
     safe work exists in its lane, the conductor must
     redirect that manager in the same tick rather than
     leaving the lane idle.
   - Run this phase once during startup and again only when
     a human changes scope, a contract changes, integration
     reveals a design conflict, or repeated worker failure
     proves the plan wrong. Do not keep reopening planning
     while safe implementation can proceed.

5. Phase 4 `TL and Uber TL review`.
   - For every manager plan or cross-packet design change
     that is about to unlock worker edits, dispatch one TL
     reviewer.
   - TL review must be findings-first and must include:
     - correctness risk;
     - integration risk;
     - test gaps;
     - file ownership conflicts;
     - missing acceptance evidence.
   - Run an Uber TL pass using `l8()` semantics over the
     combined design during startup and again only when
     cross-team architecture, contracts, or safety
     assumptions materially change. Do not stall unrelated
     safe packets waiting on a full-board rerun when their
     reviewed scope has not changed.
   - Record pending and completed reviews in
     `RUN_REVIEW_QUEUE_PATH` when that artifact is
     materialized.
   - No implementation worker may start for a packet with
     unresolved P0 or P1 review findings on the packet's
     relevant plan or diff.
   - Security and privacy review is required for every
     packet described in `Security And Privacy Gate`.

6. Phase 5 `Implementation dispatch`.
   - Create or reuse isolated worker worktrees under
     `WORKER_WORKTREE_ROOT` when a packet needs write
     isolation, branch isolation, risky experimentation, or
     parallel fanout. In `same_thread` mode, a low-risk
     packet with sole ownership of its files may be executed
     directly by the conductor in the active implementation
     worktree, but the event log must record that the
     conductor held that write scope for the tick.
   - Assign one edit-capable worker per disjoint write
     scope.
   - Treat lower-level implementation, test design, browser
     evidence capture, and focused debugging as SWE work by
     default. Do not keep those tasks in the conductor or in
     an M1 manager when safe worker dispatch can carry them.
   - Treat long-running lint, build, test, browser
     validation, screenshot capture, CI polling, and PR
     health checks as verification, evidence, or delivery
     worker work by default. The conductor may run them
     same-thread only for short local checks, emergency
     unblockers, or tool limitations; otherwise it delegates
     the command and continues managing active lanes.
   - When a code-generation packet and a collaboration,
     validation, or evidence packet are simultaneously safe
     under the same manager, dispatch them in parallel if
     their scopes do not conflict.
   - For a runnable packet attached to an active blocking
     gate, prefer dispatching both the code lane and a
     parallel verification or evidence lane before taking
     more top-thread planning work.
   - Collaboration-artifact generation is a first-class SWE
     activity when it produces reviewable artifacts that
     accelerate integration, verification, or resume:
     screenshots, browser logs, validation transcripts,
     concise diff summaries, contract notes, and handoff
     bundles.
   - For every active M1 manager with a safe ready packet
     and idle worker capacity, dispatch at least one
     lower-level SWE under that manager in the same tick or
     the next productive tick unless a recorded blocker,
     lease conflict, or missing contract prevents it.
   - For every active M1 manager with more than one safe
     disjoint packet and remaining capacity, dispatch more
     than one lower-level SWE under that manager before the
     conductor takes that work back locally.
   - Use bounded practical fanout up to the active capacity
     limits. Do not leave capacity idle while safe packets
     can move unless the tick records the lease, risk, or
     capability reason.
   - Dispatch only through an adapter operation recorded in
     `RUN_EVENTS_PATH`.
   - If at least one edit-safe packet exists and worker
     capacity is idle, dispatch at least one edit-capable
     worker or take a recorded same-thread conductor edit in
     the same tick unless a recorded blocker, lease
     conflict, or missing contract prevents it.
   - Default implementation workers to `gpt-5.3-codex-spark`
     with `xhigh` reasoning.
   - Tell every worker:
     - they are not alone in the codebase;
     - they must not revert edits made by others;
     - they must stay inside their write scope;
     - they must stop and report if they need another
       manager's files;
     - they must stop and report if a required contract,
       interface, fixture, or acceptance row is missing;
     - they must record changed paths, commands, failures,
       and residual risk.
   - Tell every M1 manager:
     - they are expected to create or supervise real SWE
       execution, not only summarize or restate plans;
     - they are responsible for routinely checking their
       workers, redirecting idle capacity, and turning
       deliberation into code, tests, evidence, meeting
       logs, PRDs, design docs, or concrete blocker reports;
     - they should keep worker write scopes disjoint when
       running in parallel;
     - they should aggressively split safe code generation
       and collaboration-artifact work into parallel SWE
       lanes whenever capacity allows;
     - they should return accepted patches, concrete review
       findings, or concrete blockers quickly;
     - they should escalate only the cross-team decisions
       that truly require conductor attention.
   - Extra workers may run read-only triage, test design, or
     evidence capture when there are fewer safe edit scopes
     than worker slots.

7. Phase 6 `Manager integration`.
   - Managers review worker outputs before integration.
   - A TL reviewer must review every worker diff before it
     is integrated.
   - Record accepted and rejected integration decisions in
     `RUN_DECISION_LEDGER_PATH`.
   - The integration manager ports accepted diff artifacts,
     accepted worker commits, or accepted same-thread
     conductor changes into the current integration surface.
   - Do not merge two packets that edit the same file until
     the owning managers reconcile the conflict in writing.
   - Shared-file packets must integrate in the lease order
     recorded on the board or as explicit stacked patches.
   - After each integration, run the smallest relevant
     targeted test set from the plan.
   - If integration reveals architectural conflict, return
     to Phase 4 for TL/Uber TL review of the revised design.
   - Record the last known good integration commit after
     every passing targeted validation run.

8. Phase 6.5 `Design iteration loop when declared`.
   - Run declared hands-off UI iteration loops before final
     browser evidence and after every integrated UI surface
     that the plan marks as iteration-sensitive.
   - The Visual Designer critiques hierarchy, contrast,
     density, grouping, typography, icons, spacing, state
     tokens, and visual polish.
   - The UI/UX Designer critiques flow, affordance, direct
     manipulation, consistency, user control, error
     prevention, recognition over recall, target sizing, and
     choice complexity.
   - The UX Tester runs scripted task walkthroughs and
     records friction, failed tasks, timing when useful,
     keyboard-only gaps, mobile fallback gaps, and
     screenshot or pixel evidence.
   - The triad produces ranked fixes. Edit-capable workers
     may implement only accepted fixes for the current
     iteration.
   - Re-run the loop until the plan's stop condition is met
     or the loop is blocked with owner and next action.
   - Record before/after evidence under the run log artifact
     directory.
   - Record HCI findings, accepted fixes, rejected fixes,
     before/after evidence, and stop-condition status in
     `RUN_HCI_DASHBOARD_PATH`.

9. Phase 7 `Verification and browser evidence`.
   - Verification owns targeted tests, the repository's
     documented prepare and verify commands, and browser
     smoke evidence.
   - Browser evidence must cover desktop and mobile.
   - For browser-facing products without a declared durable
     demo domain, Verification and Delivery must prefer
     localhost demos served from the active implementation
     worktree for operator-visible progress, smoke, and
     non-terminal handoff.
   - If a product plan declares a durable demo domain owned
     by the run, that domain becomes the canonical human
     demo, PR proof, and handoff surface after the
     corresponding routing/deploy slice is merged and
     deployed. Localhost remains the exact-worktree
     pre-merge proof surface and fallback when the durable
     route is not yet available. When both surfaces exist,
     report the durable domain first and localhost second as
     proof-only or fallback evidence.
   - While a browser-facing stream is actively implementing
     features, do that work in the implementation worktree.
     Do not move back into the main worktree for ordinary
     coding, demo refreshes, or browser evidence unless the
     human explicitly redirects execution there.
   - When a browser-facing packet lands a runnable slice,
     surface the canonical demo URL in the tick evidence and
     handoff. If the run is using localhost for pre-merge
     proof or fallback diagnostics, also record the fresh
     localhost URL and route. If the preferred port is busy,
     choose the next free port and record the exact URL.
   - Single Current Demo Rule: every browser-facing run has
     one canonical current demo URL recorded as the active
     `demo_session`. If the plan declares a durable demo
     domain, that domain is the canonical demo URL and
     localhost is recorded separately as validation or
     fallback evidence. Evidence may use additional URLs
     only when the event explains why, and any replaced demo
     URL must be marked stale or stopped in the run events.
     A browser-visible tick cannot count against a gate if
     its evidence came from a stale URL, stale build
     revision, or a different worktree than the code being
     claimed.
   - Use two proof levels:
     - Quick proof is the smallest targeted check that
       confirms the active gate moved or the active bug is
       absent. It is expected after each small runnable
       slice.
     - Full proof is the declared browser suite or
       equivalent multi-gate validation for the product
       surface. It is required before browser-visible PR
       updates, handoffs, risky shared-runtime changes, or
       claims that a blocking gate is green.
   - For browser-visible slices, capture fresh screenshots
     or equivalent visual proof from that exact localhost
     build and link them in the evidence set. Reused or
     stale screenshots do not satisfy visible-progress
     proof.
   - Canvas smoke must include nonblank pixels, usable
     framing, and no incoherent overlap.
   - Renderer evidence must cover local preview, declared
     local or remote render paths, inactive bridge behavior,
     timeout, invalid request, and error paths. When a
     project explicitly defers a remote deployment proof,
     the remote row is recorded as deferred and must not
     block unrelated editor-dynamics work.
   - Verification evidence must include exact command, cwd,
     worktree path, commit SHA, exit code, timestamp, stdout
     and stderr artifact, browser viewport, device scale
     factor, route, screenshots, pixel proof, render
     response artifacts, hashes, row status, owner, and next
     action.
   - Link all verification artifacts from
     `RUN_EVIDENCE_BROWSER_PATH`.
   - If the repository's documented commands are
     unavailable, record the exact command and blocker. Do
     not substitute host-shell validation.

10. Phase 8 `Delivery`.
    - Reconcile canonical events, board state, cockpit
      artifacts, reviews, evidence rows, and plan status.
    - Reject stale evidence using `Evidence Freshness`.
    - Create, update, push, or mark PRs ready for review as
      coherent reviewed slices become available. Record
      branch, commit, PR URL, chain parent, check state, and
      next tick intent in a non-stopping delivery event
      record. The structured delivery event must also
      include gate ids, validation commands and results,
      proof artifact paths, canonical demo URL, any
      localhost proof URL, build or commit revision, PR
      visibility state, and the next concrete product slice.
    - Apply the PR Portfolio Pressure Contract before
      opening another disjoint PR. Prefer updating the M1's
      current PR slot, stacking on an explicitly recorded
      parent, merging ready lower-risk PRs, or superseding
      stale PRs so the active review set trends back toward
      one to three open PRs.
    - Do not sit on large validated local diffs during an
      active browser-facing stream. After a coherent
      reviewed slice is linted and validated, commit and
      push it to the active PR or the next PR in the chain
      promptly so remote review state stays close to local
      truth.
    - Apply the Local Lint Discipline Contract before every
      commit and push. The non-stopping delivery event must
      name the lint commands, lint scope, whether broad repo
      lint was required, whether lint rewrote files, and the
      final pre-push lint result. CI may still find deeper
      issues, but PR creation or update must not be the
      first lint workflow for avoidable local failures.
    - Every browser-visible PR update must link fresh visual
      proof from the current branch state, normally the
      declared durable demo URL, localhost screenshots,
      report artifacts, or both. A PR update without fresh
      proof is not complete delivery hygiene for that slice.
    - Reviewer-Visible Proof Preference: when a PR is the
      review surface for browser-visible work, prefer a PR
      comment or PR body update that links the proof
      artifacts directly over burying proof only in local
      run logs. If proof cannot be linked because the
      artifact is local-only, the PR update must describe
      the exact command, commit, URL, and artifact path.
    - After a PR lands or is replaced, and further feature
      work remains, spawn or reuse a fresh implementation
      branch from the latest `origin/main` in the active
      implementation worktree or devcontainer before the
      next coding wave. Record the new branch in the
      non-stopping delivery event and resume artifacts.
    - Stack vs Fresh Branch Rule: stack only when the next
      slice semantically depends on the unmerged PR and the
      chain parent is recorded. Start from fresh
      `origin/main` when the previous PR has landed, is
      superseded, or the current branch is materially stale
      relative to `origin/main`.
    - Treat pending PR checks as health data unless a
      concrete failure blocks all safe next work. Return to
      the conductor loop after PR delivery-event work when
      the invocation iteration goal is unmet.
    - Prepare final handoff with completed packets, changed
      paths, accepted diff artifacts, validation evidence,
      screenshots, render proof, unresolved blockers, and
      next owner for every open risk.
    - Refresh `RUN_RESUME_COCKPIT_PATH`,
      `RUN_RESUME_PROMPT_PATH`, and
      `PLAN_RESUME_PROMPT_POINTER_PATH` before any pause
      handoff, non-stopping delivery event record, or
      terminal handoff.
    - Mark `terminal_completed` only when every required
      packet is completed, zero release-blocking acceptance
      rows remain, evidence is fresh, and required final
      signoffs are present.
    - Mark `terminal_partial_handoff` when remaining blocked
      packets are accepted for handoff with owner, reason,
      next action, and human-readable resume path.
    - Mark `terminal_blocked` only when no incomplete packet
      can move without human decision, adapter capability,
      external service, or revised scope.
    - If no terminal state applies, return control to the
      conductor tick loop.

Status rules:

- Run lifecycle state and packet state are separate. A run
  can be `verifying` while some packets are `completed`,
  some are `verification`, and some are `blocked`.
- Allowed packet states:
  - `pending`.
  - `manager_planning`.
  - `tl_review`.
  - `ready_for_workers`.
  - `in_progress`.
  - `integration_review`.
  - `verification`.
  - `completed`.
  - `blocked`.
- `terminal_completed` is not a packet state. It is a run
  state and requires zero release-blocking rows.
- Accepted blockers move the run toward
  `terminal_partial_handoff`, not `terminal_completed`.
- A packet can be `completed` only when its acceptance gates
  are backed by command output, browser evidence, render
  artifact evidence, or review signoff.
- An accepted blocker never counts as `completed`. It
  remains `blocked` with owner and next action.
- A manager may not mark a packet `completed` based on
  intent alone.
- Allowed state transitions:
  - `pending` to `manager_planning` by MoM.
  - `manager_planning` to `tl_review` by owning manager.
  - `tl_review` to `ready_for_workers` by TL reviewer.
  - `ready_for_workers` to `in_progress` by owning manager.
  - `in_progress` to `integration_review` by worker and
    owning manager.
  - `integration_review` to `verification` by TL reviewer
    and integration owner.
  - `verification` to `completed` by Verification Manager
    and Delivery Manager.
  - Any state to `blocked` by MoM, manager, TL,
    Verification, or Delivery when required evidence or
    capability is missing.
- A packet stale in one state for a full reporting interval
  must be called out in the run log with owner and next
  action.

Failure handling:

- Stop the phase if a P0 review finding is found. Stopping a
  phase does not end the run; it creates a conductor tick
  with blocker, owner, and resume path.
- Keep worker diffs intact when validation fails.
- Do not use destructive git commands.
- Do not silently broaden file scopes.
- Do not continue feature edits, risky validation, or run
  artifact writes from a shared or protected checkout that
  the run has marked read-only or bootstrap-only.
- Retry a failed packet at most twice without human input.
  After two failed attempts, split the packet, reduce scope,
  or escalate to the human.
- Quarantine failed worktrees until Delivery records whether
  to abandon, retry, or mine them for partial patches.
- Revert only integration patches created by the current
  run, and only by applying a forward repair or an explicit
  non-destructive revert patch in the integration worktree.
- Escalate to the human before expanding scope, adding new
  config surfaces, accepting missing external services as
  release-ready, or changing a shared protected checkout's
  branch state.
- If a manager or worker fails, record:
  - agent id when available;
  - assigned packet;
  - last status;
  - exact failure;
  - whether another worker can safely retry.
- If a PR check fails, record the check name, URL or run id,
  failing commit, suspected owner packet, and next repair
  tick. A failing check blocks only the packets that depend
  on that failure unless it makes every safe next packet
  unsafe to move.

Completion criteria:

- `terminal_completed` requires all required packets
  completed, zero release-blocking acceptance rows, fresh
  evidence, and final signoffs.
- `terminal_partial_handoff` requires every incomplete
  packet blocked with owner, reason, next action, accepted
  handoff state, and resume path.
- `terminal_blocked` requires an explicit reason no packet
  can move without human decision, adapter capability,
  external service, or revised scope.
- Uber TL review has no unresolved P0/P1 findings.
- Verification has recorded targeted tests, prepare, verify,
  and browser evidence, or exact blockers.
- Delivery has reconciled the orchestration document and
  live worker plans.
- The final response identifies the run log, plan path,
  changed paths, validation status, and remaining risks.
- If the run is not terminal, the final response must use
  the pause handoff schema below and must not imply the plan
  is complete.

Turn-Based Harness Continuation Contract:

- Some agent harnesses are turn-based: emitting a
  natural-language message ends the agent's turn and yields
  control to the human. In such a harness, a status,
  checkpoint, or "should I continue?" message between
  packets is an early-stop violation, even when phrased as
  progress.
- While a run is non-terminal, do not emit a human-facing
  message between packets or gates. Continue with tool
  calls: select the next packet, then author, build, test,
  lint, commit, push, and advance.
- A delivery event such as a commit, push, pull request open
  or update, or green test is a checkpoint inside the loop,
  never a reason to return control.
- Emit a human-facing final message only on genuine terminal
  state, a true blocker that stops every safe next packet
  (recorded with the exact resume command), or an explicit
  human pause or stop.
- A runtime Stop gate may enforce this, but installing one
  is a human decision: an agent must not self-install a hook
  that blocks its own stopping, because that removes human
  approval gates. The operator may add such a gate (for
  example a Claude Code Stop hook) keyed off a run sentinel
  at `.agents/local/m2-active.json` with a bounded
  auto-continue budget. The conductor only writes the
  sentinel at run start and removes it at terminal state; it
  never installs or modifies the gate itself.
